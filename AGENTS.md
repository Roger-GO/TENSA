# AGENTS.md — Project Conventions

This file is for any agent (human or AI) working in this repo. Read it before touching code.

## Project shape

- **Layout**: `server/` is the Python substrate package (PEP 621 + src layout, hatchling build backend). `web/` is the v0.1+ React UI (Vite 6 + React 19 + TS + Tailwind v4 + Radix; pnpm). The two are independent packages with their own CI workflows.
- **All file paths in commits, plans, and reviews are repo-relative.** Never use absolute paths in code, docs, or commit messages.

## Pinned versions

- **Python**: 3.12+ (development on 3.12; CI runs 3.12 and 3.13 on Linux, macOS arm64, and Windows)
- **FastAPI**: `>=0.133,<0.143`. FastAPI can break callers in a minor release, so the cap is the next minor after the newest one the suite ran against; raising it means running the whole suite in an environment that holds the new release.
- **Starlette**: `>=1.3.1,<2`, declared directly. FastAPI no longer caps it, and the floor is what keeps the published advisories (the `FileResponse` range DoS, the Windows `StaticFiles` path lookup, Host header and form limits) out of a fresh install.
- **ANDES**: `>=2.0,<3.0` (2.0.0 is the verified-against version; `server/ANDES_VERSIONS.md` tracks the fourteen API contracts the substrate depends on)
- **pyarrow**: latest stable (pinned in pyproject.toml at install time)
- **pydantic**: v2

ANDES upgrades are deliberate — never accept an automatic minor bump without re-running the curl walkthrough in CI.

Other updates arrive as weekly Dependabot pull requests (`.github/dependabot.yml`, which proposes only patch releases of ANDES). `.github/workflows/audit.yml` runs `pip-audit` on a fresh install of the server with its `mcp` extra and `pnpm audit --prod` on the web lockfile every week and whenever a dependency file changes; both only report for now.

## Architectural decisions (do not relitigate without a plan revision)

- **Substrate is Python-API-direct, not CLI-shell-out.** ANDES CLI is too thin for disturbances; we call `andes.load`, `ss.PFlow.run()`, `ss.TDS.run()`, etc. in-process from a subprocess worker.
- **Per-session subprocess + two `multiprocessing.Pipe`s (data + control).** Threads-in-process rejected (ANDES is GIL-bound and stateful).
- **TDS streaming via the `TDS.callpert` per-step hook.** No `streaming_step` monkey-patching. There is no credit protocol and the solver never waits for a client: the only pacing is the blocking write to the data Pipe, which follows the parent's reads. Each attached client has a bounded inbox, and one that falls behind gets a `resync` rather than a stream with frames missing. A daemon thread in the worker mirrors the abort event into a flag that `callpert` checks, independent of the data Pipe.
- **All disturbances (Fault, Toggle, Alter) require pre-setup state.** Single endpoint `POST /sessions/{id}/disturbances`. After PF/TDS commits setup, callers must `POST /sessions/{id}/reload` to add more — there is no fast-reload path; `andes.load(setup=False)` is the only mechanism.
- **`PFlow.run()` and `TDS.run()` do NOT auto-call `setup()`.** The wrapper calls `ss.setup()` explicitly first if `not ss.is_setup`. Verified against ANDES 2.0.0; PFlow.run on a non-setup System raises `IndexError`.
- **HTTP boundary uses ANDES `idx` + `name` directly.** No opaque substrate-ID layer. Researcher persona already knows `idx` from notebooks; abstraction adds friction without protecting against an actual ANDES API change (covered by the version pin).
- **Apache Arrow IPC over WebSocket for time-series.** N-rows-per-batch default; anti-aliased boxcar mean default with `?decimation=none` opt-out.
- **No authentication.** The app trusts the local OS user, binds to loopback by default, and warns loudly on non-loopback binds. WebSocket protocol: connect → server sends `{"type":"ready"}` → client sends its first command frame.

## Security posture

The trust model lives in the top-level docstring of `server/src/tensa/__init__.py` (canonical statement) and in `SECURITY.md`. Summary:

- **Local OS user is trusted** — case files contain Python expressions evaluated by ANDES at parse time, and the local user is the only authorized actor.
- **Loopback web origins from random browser tabs are NOT trusted** — defended via Host/Origin pure-ASGI middleware + precise CORS allow-list (no wildcards, no `null`, no extension origins).
- **Third-party case files are NOT trusted by the system** but ARE trusted by the user when they choose to load them. ANDES's secondary file reads are logged via `sys.audit` (best-effort, Python-level only — does not catch C-extension reads).
- **Network exposure is opt-in and unauthenticated** — `--bind 0.0.0.0` exposes the full API; users who need remote access on untrusted networks should front the server with an authenticating proxy or tunnel.
- **Windows**: workspace boundary is best-effort; warning emitted at startup.

## Doing the work

- **Patterns to follow** are listed per implementation unit in the plan. Read them before coding the unit.
- **Test-first signal** — when a plan unit carries an `Execution note: Start with a failing integration test...` line, honor it.
- **Tests live alongside the package**:
  - `server/tests/{unit,integration,acceptance}/` — Python; acceptance tests run only with `pytest -m acceptance`.
  - `web/tests/{unit,e2e}/` — TypeScript; `pnpm test` (Vitest) for unit, `pnpm test:e2e` (Playwright) for e2e. The e2e tests drive the real UI against a real `tensa serve`; `web/playwright.config.ts` says how to start it, and the `e2e` job in `web.yml` runs them in CI. A spec takes `test` and `expect` from `web/tests/e2e/fixtures.ts`, not from `@playwright/test`: that `test` ends the sessions the test's pages opened, which a page closed by the test runner does not, so the suite does not fill the server's session cap. A timeout in the web suite guards against a test that never ends and says nothing about speed: `web/vitest.config.ts` sets the default and has the rule (no test needs more than a quarter of its timeout on a runner of a few cores with coverage on, which is what CI is). What a test holds of speed it holds as work, which is the same on every machine: the steps of `tidyRoutes`, or a number of pictures of the diagram (`pictureTime` in `web/tests/unit/helpers/diagramStates.ts`). An e2e spec does not know a number the solver computes beforehand; it reads it from the response and holds the page to that.
  - `scripts/ci-matrix.sh [all|lint|unit|smoke|full|acceptance]` runs the CI stages locally (`acceptance` is the slow end-to-end suite and is not part of `all`). The `smoke` marker tags the one cross-platform test (real server, worker, PF, short TDS) that macOS and Windows run besides the unit tests. Coverage: `pytest --cov` in `server/`, `pnpm test:coverage` in `web/`.
- **Style**:
  - Python: `ruff check` (lint) and `mypy --strict` (types) on `server/src/`. Both must pass before commit.
  - TypeScript: `pnpm lint` (ESLint, `--max-warnings 0`) and `pnpm typecheck` (TS strict + `noUncheckedIndexedAccess`) on `web/`. `pnpm format:check` (Prettier) must pass.
- **Commits are conventional** (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`). Scope is the implementation unit name when applicable: `feat(unit-3): FastAPI app skeleton + auth`.
- **Never use `git add .`** in this repo. Stage files explicitly per logical unit.

## web/ conventions

- **Package manager**: pnpm 11+. Install with `npm install -g pnpm` or `corepack enable`. The lockfile is checked in; `pnpm install --frozen-lockfile` runs in CI.
- **Node**: 22 LTS minimum (newer versions also work).
- **Component conventions**: 2-space indent, single quotes, trailing commas (Prettier-enforced). Named exports only — no default exports for components. Components in `src/components/<scope>/<Name>.tsx`; tests at `tests/unit/components/<scope>/<Name>.test.tsx`.
- **Styling**: Tailwind v4 utility classes only. Color/type/spacing/motion tokens live in `web/src/styles/tokens.css` (Unit 2 fills it in) and resolve via Tailwind's `@theme`. Never hardcode colors / spacing values in components — always go through tokens.
- **Radix wrappers** (`web/src/components/ui/*`) forward Radix's behavior unchanged and apply project tokens via Tailwind. Never re-implement Radix logic. Falsification gate (Unit 2): if the project-built component library doesn't out-look stock shadcn-with-tokens, downgrade.
- **API client**: types are codegen'd from the substrate's `/openapi.json` via `pnpm regen-api-types` into `src/api/generated.ts` (committed). Hand-authored brands (`SessionId`, `RunId`) live in `src/api/types.ts`.
- **Query hooks**: `src/api/queries/` holds one module per domain (`case.ts`, `elements.ts`, `snapshots.ts`, ...), and its `index.ts` re-exports them all. Import hooks from `@/api/queries`, never from a module of the folder: tests mock that path, and an import that reaches past it runs the real hook. A helper only the modules share (`jobGlue.ts`, `caseReady.ts`) stays out of the barrel, and `web/tests/unit/api/queriesSurface.test.ts` pins what the barrel exports.
- **`/api/*` prefix**: the Vite dev proxy strips `/api` and forwards to the substrate's root paths. Production (Unit 10) prefixes the substrate's routers with `/api` so the same client URL works in both modes.

## What goes where

- `server/src/tensa/api/` — FastAPI routers, schemas (`schemas/`: one module per domain, each model exported from `schemas/__init__.py`, which is what the routes import from), app factory
- `server/src/tensa/api/body_limit.py`: a route class that refuses a body over a cap in bytes before it is read. FastAPI reads, parses and checks a JSON body on the event loop before the route or any dependency of it runs, so a route that takes long series (`POST /comtrade`, `POST /response-metrics`) gets its router from `body_limited_route`, with a cap worked out from its own cap on values (`json_number_bytes`)
- `server/src/tensa/core/` — `wrapper/` (the `Wrapper` class: `__init__.py` puts it together from one mixin per routine, in `pflow.py`, `tds.py`, `eig.py`, `cpf.py`, `se.py`, `elements.py`, `clone.py`, `snapshot.py`, `sweep.py` and the other modules beside it, over the shared state in `base.py`, and re-exports every name the single-file module had, so `from tensa.core.wrapper import ...` keeps working; a new routine is a mixin in its own module that `Wrapper` lists as a base, and a test that patches a name there patches the module that uses it, such as `tensa.core.wrapper.case`), worker, session manager, Arrow streaming; `session_dirs.py` (per-session scratch dirs under `.sessions/`: owner marker, startup sweep, and `remove_tree`, which any recursive delete of workspace data should use because Windows refuses read-only files); `worker_spawn.py` (BLAS thread caps and the Windows Job Object applied when a worker is spawned); `win32.py` (the one shared `kernel32` loader with its ctypes prototypes, used by both); `sweep_pool.py` (the sub-workers a long sensitivity sweep spreads its iterations over, spawned the same way as a session's worker, and the pipe-backed abort flag they use: never share a `multiprocessing.Event` with a process that is killed, because `Event.set` then blocks forever on its dead waiter)
- `server/src/tensa/core/session/`: the `SessionManager`, put together in `__init__.py` from one mixin per concern over the shared state in `base.py` (`SessionManagerBase`, and `_Session`, the bookkeeping of one live session). `registry.py` spawns, closes and reaps sessions and sends a session's worker its requests (`invoke`, `invoke_streaming`); `jobs.py` is what the job registries show the routes, the live feed of job transitions, `cancel_session_job` and the liveness sweeper; `runs.py` keeps a streaming TDS run for a client that drops and attaches again, and `sweeps.py` does the same for a sensitivity sweep; `errors.py` has what the manager raises and `buffers.py` the run and sweep buffers. `tensa.core.session` re-exports every name the single-file module had, so `from tensa.core.session import ...` keeps working; a new concern is a mixin in its own module that `SessionManager` lists as a base, and a test that patches a name there (a tick, `SweepWorkerPool`, `attach_kill_on_close_job`) patches the module that uses it, such as `tensa.core.session.registry`
- `server/src/tensa/security/` — workspace path validation, portable file-name validation (`names.py`: use it for any client-supplied name that becomes a file name; `user_name_problem` is the single rule behind snapshot and save-as names), Host/Origin ASGI middleware, and the ASGI middleware that adds the browser security headers to every HTTP response (`SECURITY_HEADERS`; wrapped outside the Host/Origin check so its 400s carry them)
- `server/src/tensa/core/layout.py`: the layout of a case's diagram, the document kept beside the case as `<case>.layout.json`. It holds the schema (`SidecarLayout`, version 2: the positions of buses, devices and placed controllers, the expanded state of units, busbars, branch routes, label offsets, connection faces and figure settings), `upgrade_layout`, which every read and write goes through so that a version 1 file is answered and stored as version 2, and what the save paths call so that the placement goes where the system goes: `carry_layout_sidecar` after a save under a new name (the worker's `save_case` handler and `CloneManager.save_as`), `read_layout_sidecar` and `write_layout_sidecar` for a snapshot (the layout sits in the snapshot's JSON) and for a bundle (`layout.json`). Entries are keyed by idx, and an idx can come to name another element (a `.raw` file keeps none, so a system saved as one is numbered afresh when it is read back), so a device position and the state of a generating unit carry their `bus` and a branch route its `bus1` and `bus2`: a reader uses an entry only for an element on those buses (`unitStatesOf` for a unit) and matches a leftover position or route to the element that is there now (`resolveDeviceCoords` and `branchPolylines` in `sidecar.ts`), and `for_renumbered_copy` (`layoutForRenumberedCopy` on the web side) is what the layout beside a `.raw` copy keeps. A route that was drawn by hand is told from one the diagram made: a branch by `routing: "manual"`, and the connector of a device by the `bend_points` of its entry under `connections`, which carries the `bus` the connector runs to and is read with the position of its device, under the idx that position was found under (`storedConnectorRoutes`); `for_renumbered_copy` keeps a connection that names its bus. The other sections keyed by the idx of a device or a branch (label offsets, the faces of a connection) have no reader yet, and each needs an anchor of this kind before it gets one. Two things keyed otherwise are read: the `length` of a bus's bar (`barLengthsOf`), and `connector_style` among the `figure` settings (`connectorStyleOf`, `straight` or `elbow`), which is a setting of the whole diagram and so needs no anchor. A layout is never a reason to fail a save, an export, an import or a restore: one that cannot be read or does not validate is logged or reported as a warning and left out. A layout has one size, the bytes of the form the server stores it in (`layout_json`: compact JSON with every field written out, which is what the file beside a case and a bundle's `layout.json` hold), and `MAX_LAYOUT_BYTES` is measured on that form at every way in: `PUT /workspace/layout` and the `layout` of a snapshot save or a bundle export answer 413 over it, and a file or a bundle entry that is read is held to it by the layout it holds (`check_layout_size`), not by its own length, which `MAX_LAYOUT_FILE_BYTES` only keeps readable. So what the server has taken it can write anywhere and read back; a new way in calls `check_layout_size`, and a new writer writes `layout_json`. The models are defined there, not in `api/schemas`, because the worker validates layouts too. On the web side `web/src/components/sld/sidecar.ts` mirrors the schema (`parseSidecar`, with the same upgrade; what the first screen reads of a layout, the hooks that save and restore, is in `sidecarCore.ts` beside it and exported from both, so that the rest loads with the diagram: a module of the first screen imports from `sidecarCore`), `captureLayout` turns the diagram as drawn into the document, the canvas keeps the result in the case store (`diagramLayout`), and `web/src/lib/diagramLayout.ts` is what every save sends. A new thing the diagram places means a field in both schemas, a reader in `buildGraph`, a line in `captureLayout`, and an entry in `web/tests/fixtures/layout-v2.json`, the one document the tests of both sides read (`server/tests/unit/test_layout_web_schema.py`, `sidecar.test.ts`) so that the two schemas and the two cuts for a renumbered copy cannot drift apart; `web/tests/unit/components/sld/SldCanvasLayoutRoundTrip.test.tsx` and `web/tests/e2e/layout-persistence.spec.ts` hold the rule that a saved diagram reopens as it was placed
- `web/src/components/sld/connections.ts`: where every connector of the diagram attaches and how it runs. A bus is a horizontal bar, and `layoutConnections` works out, from the nodes and edges `buildGraph` made and where the nodes are now, the bar of each bus (its length and its taps) and the route of each device connector and branch. It is pure and cheap, and the picture the canvas draws from (`picture.ts`, below) runs it on every change of the nodes, a move of a drag included; `SldCanvas` then hands the bars to the bus nodes (`data.bar`) and the routes to the edges (`data.route`); the edge components (`StubEdge`, `TopologyEdge`, `TransformerEdge`) only draw the points, and `BusNode` draws the bar and a dot per tap. The rules are in its docstring: a tap is the foot of the perpendicular when that falls on the bar and the tip otherwise, the taps of one face keep `TAP_SPACING` apart (`spreadTaps`) and the bar grows to hold them, of two that ask for places too close the one that holds its place less firmly gives way (`TAP_HOLD`: the end of a line for a device that drops square, a device for a route that runs straight on), a tap keeps the spacing from every other tap of its bar whichever face each is on (the taps of the two faces are handed out together, so two connectors never meet a bar at one place, one from above and one from below, where they would read as one line through the bus), a device has a port at the middle of each face (`DEVICE_PORT`) and leaves by the one that points at its tap, its connector keeps out of the other devices, the controller badges and the bars of other buses (where its usual ways run through one, `detourFor` steps it round: out of a side of the device, or across under the face that looks at the bar, and square onto the bar beside what is in the way, at a tap that holds its place most firmly, `TAP_HOLD.round`; the pass runs a second time, with the bars as long as they came to be, when a connector was left through something), a bar is not drawn out past a tip that the bar of the next bus or a symbol stands beside (`growLimit`: the tap of a device past that tip lands inside it), a branch with no stored route leaves by a face and never by a tip (two bars that stand level are bridged over, or under), a device is over the bar, or past its tip, by where the bar is once the routes that end on it have drawn it out, and a branch with a stored route keeps its bends while its ends are brought onto the bars (`data.bendPoints`, used only while the buses sit at `data.bendAnchors`). The run of such a route that leaves a bar moves along with its tap, and it is kept `SLIDE_CLEARANCE` from the bars the branch is not connected to: the ends that share a port are parted to the side that leaves every run clear (`TapWish.blocked`), and a run that cannot move clear stays where it is and steps across to its tap. `sides.ts` holds the sides, and `assignBranchSides`, which only the routing pass of the auto-layout still declares its ports from (`autoLayout` with `routes`, which the canvas no longer asks for). `graph.ts` uses the same pass, run over the buses and branches alone, to put a device the layout does not place over a free part of its bar, in line with what lands on the other face or a spacing clear of it (`freeColumn`), and clear of the branches that pass through its row (`branchColumns`), the narrow devices first. `layout.ts` leaves `LAYER_GAP` between two layers of buses, and gives each bus a box as wide as its bar and its devices need (`busRoom` in `graph.ts`, which is also the length a bar is drawn at unless a layout sets one: `defaultBarLengths`). The canvas needs the measured size of each device for the ports, which it takes from React Flow's `dimensions` changes and hands back as `measured`, so a node is measured once. The labels are placed from the same routes, by `web/src/components/sld/labels.ts` (pure, like the pass itself), one kind after the other and each clear of the ones before: the label of each bus (`placeBusLabels`: under its bar, over it, beside a tip, or right under or over the bar no further than `NEAR_BAR` past a tip, clear of the runs, the symbols, the other bars, the symbols of the transformers and the labels placed before; where the label with a voltage and an angle in it has no such place the name alone is looked for one, `compact`, and only a name with none stands further off; the bus gets the place as `data.labelAt`), the P / Q readout of each generator and load (`placeReadouts`: right or left of the connector, the far side of the device, beside the symbol, every device its first choice before any its second, and none where no place is clear; `data.readoutSpot`, `'none'` for one that is left off), and the flow label of each line (`placeBranchLabels` over `branchLabelPlaces`: on a straight run of the route, beside one, or turned to read along an upright run, where it covers least, `LABEL_ROOM` off the symbol of every device (`apart`), and left off where every place would put it on something; `data.labelAt` on the edge, with `turned` or `hidden`). A generator at a reactive limit carries a mark that hangs out of its top right corner (`GeneratorNode`); its room is a box of its own on every generator (`limitMarkerBox`), which every label keeps off and the checker reads. A name with no place by its bar stands where nothing of another bus is between it and the bar, no label that does not hang under its own bar stands right under another (`UNDER_ANOTHER_BAR`), and where a label comes off badly (`busLabelLack`: its name alone, or far from its bar) the labels are placed again with that one first (`BUS_LABEL_ROUNDS`). The symbol of a transformer is part of its line and comes before all of them (`placeTransformerSymbols`): the routes are held to it, and every label keeps off it. The readouts and the flow labels are placed as wide as the values they show (`readoutWidth`, `flowLabelWidth`), and only while a power flow gives them something to show. The sizes are a model, not a measurement, and `BusNode` places its label by the same width (`busLabelWidth`), so a change to how a label is drawn goes with a change there; `labels.test.ts` and `noOverlap.test.ts` hold that no label lies on a symbol, a line, a readout or another label on the example cases, and `labelProblems` and `overlapsOnScreen` in `web/tests/e2e/sldDrawing.ts` hold the same on what a browser drew. A new kind of connection means a request in `layoutConnections`, and a rule that moves an end means a case in `web/tests/unit/components/sld/connections.test.ts` and in `web/tests/e2e/sld-connections.spec.ts`, which checks the rules on what a real browser drew
- `web/src/components/sld/tidy.ts`: Tidy diagram. `tidyRoutes` routes every line and transformer afresh with the nodes where they are, and answers one polyline per branch; it moves nothing. It lays the device connectors out first (`layoutConnections` over the stubs alone) and then routes the branches one after the other, the shortest first, by A* over a grid: the lines `GRID_STEP` apart (which is also what a node snaps to and the gap of the background dots), the line of each bar (which no route runs along: a branch leaves its bar by a face and never by a tip, and two buses that stand level are bridged over or under), and the lines that just clear a bar or a device, so a way no wider than the clearances is found. The direction of travel is part of the search state, so a bend has a price (`BEND_COST`), and so has crossing another route or a device connector (`CROSS_COST`); two routes never share a grid edge, never run closer than `NEAR_LINE` side by side, and never turn on each other. Each branch is then taken out and routed again around the others (twice), two routes that cross are routed again together in both orders, and the routes around a device that was left no place for its values are routed again together with one of its places shut. The work is bounded and deterministic: it is counted in steps of the search (`TIDY_STEPS`, about a second on a diagram of a hundred buses; `TidyOptions.steps` in a test), not in time, a search that runs out of its share makes for the goal and takes the first way it finds, the later phases stop when the steps are gone, and `TidyResult` says what was left (`unrouted`, `outOfSteps`). The grid has gaps where nothing stands (`GRID_REACH`) and a most points (`GRID_POINTS`), past which it is made coarser and then refused (`tooLarge`). `TidyOptions.keepFree` lists, device by device, the places its readout can take (`readoutReserve` in `labels.ts`): a route through one costs next to nothing while the device has another, and `LAST_PLACE_COST` through the last. A change to the search wants the budget tests of `tidy.test.ts` run (a mesh of two hundred branches within the steps, a bus set far off, a diagram too large). The rules are in its docstring. What it must keep to for its answer to be what is drawn: a tap keeps `TAP_SPACING` from every other tap of its bar on either face, and no route leaves by an end of a bar, so the connection pass (`connections.ts`) has no tap to move; `tidy.test.ts` holds that on the example cases (`tests/unit/helpers/exampleCases.ts`), together with what a tidied drawing must not have (a shared run, a kink, a line in a symbol). A tap past the tip of a bar is allowed where a bus has no place left (`MAX_OVERHANG`), though never towards a bus that stands level for the branch between the two, whose bars would meet. `TidyOptions.keep` hands it routes that stay as they are and `within` the part of the diagram to read, which is how the canvas has one branch routed round the rest (`routing.ts`, below); `preferFree` lists places a route keeps out of where it costs it no more than a bend (the labels of the buses). `alignToGrid` is the part of Tidy and re-layout that moves buses. `web/src/components/sld/tidyPlan.ts` (pure) is what both commands work out before the canvas changes anything: `planTidy` gives the nodes where they will stand and the routes (a re-layout puts every device over or under its bar, `deviceDetour: 0` to `buildGraph`), and `branchesThroughSymbols` lists the branches drawn through a symbol or a bar, which the Tidy diagram button counts. A plan that moves nothing leaves no line worse off: a line whose route holds as the diagram draws it (on nothing, and found by the router) gets another only where that one is no longer, has no more bends, is crossed in no more places and is less of one of the three; the lines that would come off worse or change for no gain keep their routes and the ones that gained are routed again around them (`KEEP_ROUNDS`, within `KEEP_STEPS` of the steps), and `TidyPlan.left` names the lines that stayed, which the notice counts. Mending a line whose route does not hold (drawn the plain way, or on something) comes before that: no round is made with no steps left for it, the last one, which leaves every route that holds and routes only the rest, has steps of its own (`LAST_STEPS`), and a plan that leaves such a line unmended where an earlier plan had mended it is not taken, the earlier one is, though it changes a line for no gain. `tests/unit/helpers/tidySweeps.ts` holds the three example cases to the first after any device was moved (`tidyKeeps*.test.ts`), and `tidyMends118.test.ts` the 118-bus case to the second, drawn as a layout has it that came without the routes of its lines. Both commands start their plan through `startTidy` (`tidyClient.ts`), which makes it within the call for a diagram of up to `TIDY_AT_ONCE` branches and in a worker (`tidy.worker.ts`) for a larger one, where the button says Tidying and a Stop beside it calls the work off. The canvas (`applyTidy` in `SldCanvas.tsx`) hands the routes to the case store as `routeOverrides`, a branch that got none keeping the route it had, each with the positions of its two buses as anchors; `buildGraph` draws a route that has anchors exactly while both buses stand there (`bendAnchors`), wherever its ends lie on the bars, and `storedBranchRoutes` gives the routes of a saved layout the same anchors from the layout's own coordinates. The route of a transformer has room for its symbol: the search for one has a second layer of states for the ways that have a straight stretch as long as the symbol with the symbol on nothing in the middle of it (`roomAt`, `spotOn`), it lands only by such a way, the place is kept while the route is taken up so that no other route runs through it (`symbolZone`), `TidyResult.spots` says where it is, and `TidyOptions.symbols` hands in the symbols of the transformers among `keep`. A route does not run where its own bar comes to be drawn out for the tap it lands on (`Terminal.grows`). `TidyOptions.only` names the branches to route when that is not all that have no route to keep. Their `ariaLabel` ends in the words a connector or a line of the case ends in, since the overlap check of the e2e tests reads the diagram by them. `web/src/components/sld/draftPlace.ts` says where a draft stands: `draftPlace` for a drop (the rules and the picture a dropped device is held to, and beside the lines where it can: a draft makes no line re-route, `drawsUndisturbed` in `picture.ts`), `settledPlaces` for one that something came to stand on, and `connectedPlace` for one that was given its bus in its form, which brings it into the row beside that bus when its connector would be long or a diagonal, cross other lines or run over something. The form is `web/src/components/inspector/DraftInspector.tsx` (`ElementForm` with `live`), shown by `RightInspector` while a draft is picked and no element is selected; picking goes through `selectDraft` in `web/src/components/sld/draftActions.ts`, which lets go of the element. An element added from a draft takes its place through `placements` of the store, which `SldCanvas` turns into a drag override. The no-overlap rule is held with drafts on the diagram by `web/tests/unit/helpers/draftSweeps.ts`.
- `web/src/components/sld/wiring.ts`: connecting on the diagram by a drag, as far as it needs no canvas. Three gestures end on a bus: a component dropped on one (a row of the palette, or a draft that is dragged there), a line or a transformer drawn from one bus to another, and the end of the connector of a device dragged to another bus. `busBars` and `busAt` say which bus a place is on (a bar is a few pixels thick, so a place counts within `BUS_HIT_PX` on screen, and the nearer of two bars is meant), `busDroppedOn` which bus a row of the palette was dropped on (the bar in reach first, and with none the bus whose name or node the place is on, since a drop is aimed at the name as readily as at the bar), and `busUnderBox` which bar a dragged symbol lies on. `attachDraft` is what connecting a draft sets on it (`bus`, or the first open end of a branch) and `moveToBus` what moving a generator, load or shunt of the system asks of the server: an edit of `bus` on every model of the generating unit that names the bus itself, with `Vn` taken along for a model that was rated for the bus it leaves. Those edits go through `useEditElements` (`web/src/api/queries/elements.ts`), which sends them in order, reads the topology again once, and takes back what it made when one is refused, so a unit is never left half moved; Undo then takes them back one request at a time, as the substrate does. `web/src/components/sld/SldWiring.tsx` is what is drawn for it, as a child of `<ReactFlow>` beside `SldRouteEditor`: the bar a drop would land on, the ring at the bar end of the connector of the selected device (none while a route is moved by hand, whose handles lie there), and, while a bus is picked (`WiringMode`: `draw` or `move`), a named button over every bar and a dashed line to the pointer, with its bar in the slot `SldCanvasHint` leaves above the diagram. A bus is picked by a press on it and by a drag that ends on it, so every gesture also works as two clicks and from the keyboard. `SldCanvas` holds the mode (`wiring`), starts it from the two buttons over the diagram (`SldDrawTools`), the commands `draw-line` and `draw-transformer` of `store/sld.ts`, the right-click menus and a Line row dropped on a bus, and acts on what was picked: a line that is drawn is a draft with both its buses (`drawBetween`), a draft is given its bus through `connect` of the draft store (which also counts the change, so the form the Inspector has open on that draft is opened afresh), and a device of the system is edited (`moveTo`). What was put on a bus on the diagram is then brought beside it by `connectedPlace`, with `slant: SLANT_PUT_ON_BUS` so that its connector drops square where the row of the bus has a place: a draft in the settling the canvas already does for drafts (`givenRef`), a device of the system in an effect of its own that compares the bus of every device with the one it was on in the topology before (`hungRef`), and acts only when the canvas sent it there (`movedRef`) or the edit journal counts an edit since, because the system of a case that is being opened is drawn for a moment under the name of the case before it. Until that effect has looked at them the device is drawn where it stood, on a connector that reaches across the diagram, and the routes that picture makes round the connector are not kept (`inTransit`, which the effect that keeps `picture.changed` reads): kept, they would stay after the device is beside its bus. The palette says which kind is being dragged (`paletteDragKind` in `store/sld.ts`), since a drop target cannot read the payload before the drop. A new gesture that ends on a bus is a `WiringMode` or a caller of `busAt`, and a new thing it changes is a function in `wiring.ts` with a case in `wiring.test.ts`; `SldWiring.test.tsx` and `SldCanvasWiring.test.tsx` hold the overlay and the canvas, `tests/unit/helpers/wiringSweeps.ts` (`noOverlapWiring*.test.ts`) the no-overlap rule through every one of these on the example cases, and `web/tests/e2e/connect-by-drag.spec.ts` all of it in a real browser.
- `web/src/store/reloadedCase.ts`: the case a reload of the page interrupted, which the page opens again. A reload starts an empty session (`useSessionRelease` gives the old one back as the page goes), so the page comes up with no case; the slice keeps a mark of what the tab has open in `sessionStorage` (`tensa:open-case-v1`: a case file with the dynamic files it was opened with, or a system built from scratch), and a mark found when the page starts is a case that was open when the page went away (`closed`). The mark follows the open case through the cascade in `web/src/store/index.ts` (`follow`): written for a case or a blank system, removed when the user closes the case. `web/src/api/useReopenAfterReload.ts`, mounted once from `App.tsx` beside `useSessionRecovery`, opens it again once the new session is there: it loads the file, or recreates the blank system, and replays the edits the tab kept (`journalBeforeReload` in `web/src/store/editJournal.ts`, which writes the journal to `sessionStorage` on every change, `tensa:edit-journal-v1`) through the same pieces a session recovery uses (`web/src/api/restoreEdits.ts`). What cannot be put back is said in a notice and the mark is dropped (`forget`): a file that is gone, a blank system the server will not start, edits no replay covers. A request that ended without an answer is no such thing, and drops nothing the tab keeps. The usual one is a second reload while the case is still on its way back: the browser ends the requests of the page that goes, each fails in it as a lost connection would, and the page still runs for a moment. `web/src/lib/pageLeaving.ts` knows that from `pagehide` (`pageIsLeaving`): the hook then leaves everything as it is, and the journal writes nothing more to its kept copy, so whatever the failures lead to on that page, the next one finds the mark, the edits and the drafts the first reload kept. A server that did not answer on a page that stays is told apart from one that refused by the error (anything but a `ProblemDetailsError`): the page stops waiting and keeps the mark (`postpone`), a replay that broke off cuts the journal for its own page only (`withoutKeeping` in `editJournal.ts`, used by `replayEditsInto`), and the notice says that a reload tries again. While the case is on its way the canvas says so where it says "No case loaded" on a first visit, and `useAddComponent` starts no blank system in its way. The e2e specs reload through `reloadWithCase` in `web/tests/e2e/fixtures.ts`, which waits for that load; a test that needs a page with no case opens another tab, whose `sessionStorage` is its own. `web/tests/unit/api/reopenAfterReload.test.tsx` holds the hook, and `left-panel-tabs.spec.ts` the whole of it in a real browser.
- `web/src/lib/commands.ts`, `runRoutine`: what a command that says Run does. The entries of the Run menu, the palette and `Ctrl+Enter` choose the routine, check that it can run now (`runReadinessNow` in `lib/useRunReadiness.ts`, the same rule the buttons read at every render), open its tab of the drawer where it runs there, and leave a request in the run-mode store (`requestRun`). The run itself is started by the component that owns the routine's Run button, which calls `useRequestedRun` (`lib/useRequestedRun.ts`) with the routines it starts: `tds/RunButton.tsx` for PF and TDS, the Analysis tabs in `analyze/AnalyzePanel.tsx` for EIG, CPF and SE. A new routine is a label in `ROUTINE_COMMAND_LABEL`, and a `useRequestedRun` where its button is. A command that cannot run yet but gives an `unavailableReason` is kept by `useMenuCommands()`, which the top bar menus and the command palette both draw: greyed out, with the reason under its name, and passed over by a click and by Enter. The eigenvalue analysis is the one routine listed that way (`eigBlocked`: no case, no dynamic-model data, no converged power flow), where the others say why on a press; a command that is left out of a list reads as a feature the app does not have, so give one that a user would look for a reason and not only a `when`.
- `web/src/lib/runLock.ts` and `web/src/lib/undoWording.ts`: the words the app has in more than one place. `runLockNotice` is the sentence for every place a run has fixed the system (why, Reset run, what it keeps, and what it loses only while `useReloadDiscardsEdits` says it would lose something), and a place that says it has a Reset run button beside it: its own (`useResetRunAction`), or `requestResetRun` (`lib/resetRunRequest.ts`, answered by `components/shell/ResetRunHost.tsx`) where no component of its own can make the request, as in a notice. `UNDO` is how a notice or a hint names Undo. A new such place uses them, so the wording cannot drift apart again. The same goes for `web/src/lib/tidyWording.ts` (the rule by which Tidy diagram keeps a route, as `betterRoute` in `tidyPlan.ts` applies it), `web/src/lib/figureWording.ts` (what the figure for a paper is called in every menu, and the line under it), `web/src/lib/savedCopy.ts` (what Save system as says of the copy it writes: the session stays on the case it had open, `savedCopy` of the case store keeps the name of the copy for the Project tab until another case is opened) and `web/src/lib/announceEdit.ts` (the notice of a changed value, with where the change is kept: through a reload of the page while the edit journal is `replayable`, and in no file until the system is saved).
- `web/src/components/ui/ClampedText.tsx`: a text held to the lines its row has, with a **More** button that opens the whole of it when it is cut (measured, and again when the row changes size), or always when it is a summary of several lines (`more`). The line above the diagram (`SldCanvasHint`), the bar of a bus pick (`SldWiring`) and the hint of a table (`DataGrid`) use it: a hint that must stay one or two lines high goes through it, not through `truncate` alone.
- `server/src/tensa/core/tds_controllers.py`: the controllers a TDS request can name (`controllers`), which is how a run closes a frequency loop without taking code from a client: a request gives parameters of a `droop` or an `ffr` (fast frequency response) on a device of ANDES's `DG` group (`ESD1`, `PVD1`, `EV1`, `EV2`), as the Pydantic models the REST body and the WebSocket's `start_tds` frame are both checked against (`parse_controllers`). `ControllerBank` binds them to the loaded System, where one that names a device the case does not have is refused; `Wrapper.run_tds` calls its `step` from the `TDS.callpert` hook, where each controller reads the centre-of-inertia or the device's bus frequency once a sample period, at the instant ANDES last solved, and writes its command in MW to the device's `Pext0`; and its `end_run` puts every input back however the run ends. `Wrapper` keeps the bank of the last run so a run that carries on from where that one stopped, with the same controllers, keeps their state. `controller_catalogue` is what `GET /sessions/{id}/tds/controllers` answers with. Its docstring gives the two laws and the timing (contract 13 in `server/ANDES_VERSIONS.md`); adding a kind of controller means a model, a branch in `_Loop.sample` and a form in `web/src/components/tds/ControllersEditor.tsx`
- `server/src/tensa/core/tds_steps.py`: which step a time-domain run is on when ANDES calls the hook. ANDES calls it before it solves the step the call names, so the values at a call are the step before. `StepClock` gives the streamed rows and a batch run's `traces` the time ANDES stored that step under, and takes the run's last step once `TDS.run` has returned; `stored_step` reads a row from the step as ANDES stored it when an event has written over the arrays since (a fault that clears puts the voltages back for the next step); `land_on_time`, called from the hook, lets a step that would end a rounding error before `tf` or an event time end on it, where ANDES is left a step it cannot take and ends the run. A record is one row per solved step and equals `dae.ts` (contract 13 in `server/ANDES_VERSIONS.md`, held by `tests/integration/test_tds_record_times.py`)
- `server/src/tensa/core/edit_log.py`: the edits a session makes to its System before setup (an element added, a param changed, an element deleted), kept in order so they can be replayed. `Wrapper` holds the log (`_edit_log`) and the rule it stands for: the pre-setup System is the case file, or an empty System, with the log applied. `Wrapper._build_system` builds that System from a log and `_adopt_system` swaps it in with the pending disturbances added back, which is all `undo_last_edit`, `redo_edit` and `delete_element` do; a file-backed `reload_case` empties the log, a blank session's replays it (either drops the pending disturbances, which the new System does not hold), and a save over the open file empties it because the file then holds the edits. A redone delete takes what the delete took the first time and is refused over anything else that has come to depend on the element. `remove_device` is the step ANDES has no call for: it takes a device out of its model's param lists and its group's registry (contract 14 in `server/ANDES_VERSIONS.md`, held by `tests/integration/test_edit_log.py` against a System read without the device). `referrers` and `dependents` find what names a device from the models' own `IdxParam` declarations, so a delete either takes its dependents with it (`cascade`) or is refused with the list; the `Fault`, `Toggle` and `Alter` devices among them are reported apart, as disturbances. A new kind of edit means an op here, a branch in `apply_op` and `step_of`, and an entry in the web journal (`web/src/store/editJournal.ts`)
- `server/src/tensa/core/dae_vars.py`: the ANDES variables a TDS run can record by name (`dae_vars`, the names `dae.x_name` / `dae.y_name` use, such as `omega GENROU 1`). The catalogue is built from the models' own definitions, so it needs no setup and asking for it does not close the case to disturbances; it leaves out the algebraic variables of a static device that a dynamic one replaces, and `resolve_dae_vars` is the one check of a request's names. The stream reads them by name from `dae.x_name` / `dae.y_name` (contract 9 in `server/ANDES_VERSIONS.md`)
- `server/src/tensa/core/response_metrics.py`: nadir, rate of change, settling time, overshoot and damping (log decrement) of a sampled signal, with the definitions in its docstring. `POST /response-metrics` (`api/routes/metrics.py`) holds no session: the web UI sends the series it plots, and a script sends a batch run's `traces`
- `server/src/tensa/core/wrapper/eig.py`, the zero eigenvalue: a system with no fixed angle reference has one, and the solver returns rounding noise for it whose sign depends on the processor (`OPENBLAS_CORETYPE=Nehalem` gives the other sign on a machine that picks newer kernels, which is how to see it). `run_eig` therefore returns an eigenvalue ANDES counts as zero (`EIG.config.tol`) as exactly zero (`_settle_zero`) with a damping ratio of 1, so no reader of the result takes it for a growing mode or a poorly damped one: the scatter's filter, the count of unstable modes in the HTML report and a script all read the sign of the real part. A result must not be given a meaning that turns on the sign of a number that is zero; `tests/unit/test_eig_zero_eigenvalue.py` and `tests/integration/test_eig_api.py` hold it
- `server/src/tensa/core/comtrade.py`: writes sampled signals as an IEEE C37.111 (COMTRADE) record, the 1999 revision with ASCII data; its docstring says what the two files hold and why. `POST /comtrade` (`api/routes/comtrade.py`) holds no session and answers with a `.zip` of the `.cfg` and the `.dat`: the web UI sends the columns of a run (the export menus of the plot and of the timeline), and a script sends a batch run's `traces`. `server/tests/_comtrade.py` is a reader written from the standard's layout, which the tests read every record back through
- `server/src/tensa/core/messages.py`: what ANDES logs while a command runs, which nothing read before. The worker installs `WorkerLogCapture` on the `andes` logger (lowered to `INFO`, contract 10 in `server/ANDES_VERSIONS.md`) and attaches what it caught to each reply and to a streamed run's frames; `SessionManager` numbers it into a per-session `MessageLog`, which `GET /sessions/{id}/messages` (`api/routes/messages.py`) reads without waiting for the worker. The text goes through `PathScrubber` before it is queued (the workspace relative to itself, the home directory as `~`, any other absolute path as `<path>`), so no server path reaches a client. `MessageLog` merges a message that repeats the newest one into it and numbers it again, so a long run's repeated warning stays one message. A sweep's (plan included) and a report's messages are left out (`UNCAPTURED_OPS`). `core/pflow_notices.py` adds what ANDES does not log after a converged power flow (a generator held at a reactive limit, a load turned into an impedance) as warnings on the `tensa.notice` logger, which the capture also listens to
- `server/src/tensa/core/codegen_cache.py` — ANDES's generated code (`~/.andes/pycode`). Nothing precomputed ships in the wheel: ANDES writes it on first use, or `tensa warm-cache` does. Holds the cache's state check (a `.tensa-warm` stamp naming the ANDES version it was checked against and the `__init__.py` it was checked for), and the background `warm-cache` child that `tensa serve` starts when the cache is missing or unchecked (`--no-warm-cache` skips it). While the child runs, a `.tensa-warm.running` marker beside the directory tells `Wrapper` to wait before it builds a System (`wait_for_background_warm`), so a case load does not race the child's generation; a server that finds a live marker starts no child of its own

Docs carry no em dashes and no emoji
- `server/src/tensa/core/logging_setup.py`: how `tensa serve` logs. `configure_logging` puts the level, plain or JSON lines (`--log-json`) and an optional rotating file (`--log-file`; a bare name goes in `~/.tensa/logs`) on the root logger, which also carries uvicorn's records because `serve` gives uvicorn no logging config of its own. Only the server process is configured: a worker reports through its replies (`messages.py`), and `worker_main` enables `faulthandler` so a native crash leaves its Python stacks on stderr. `api/request_log.py` is the outermost middleware and writes one `DEBUG` line per HTTP request and per WebSocket on `tensa.request` (uvicorn's access log stays off, so `info` is not filled by the UI's polling). `GET /api/health` (`api/routes/health.py`, which holds its own response models) reads the session registry and the code cache's stamp and never waits for a worker
- `server/tests/_crash.py`: for a test that kills a real process with a signal that dumps core (the two that send SIGSEGV to see the worker's `faulthandler` print its stack). `NO_CORE_DUMP_CODE` goes into the code of a `python -c` child and `without_core_dump(pid)` is for a process that is already running; either gives it a core size limit the kernel writes no dump for, so the suite leaves no crash report on a desktop Linux (`/var/crash`). A new test of that kind uses one of the two.
- `server/tests/_cli.py`: for a test that runs the `tensa` command line and reads what it wrote. `cli_runner()` is the one place a `CliRunner` is made, which a test holds the suite to: its terminal has no colour, takes no escape codes and is wide enough that nothing is wrapped, so what a test finds in `--help` or in a usage error does not depend on the terminal of the machine, or on a CI runner that asks for colour. The command itself writes plain text to anything that is not a terminal: Typer styles help and usage errors with Rich and takes `GITHUB_ACTIONS`, `FORCE_COLOR` or `PY_COLORS` as a reason to style them whatever they go to, so `_TensaGroup.main` in `cli.py` settles it from the two streams before each run (`_style_only_on_a_terminal`). `tests/unit/test_cli_output.py` holds both.
- `server/src/tensa/cli.py`, stopping `tensa serve`: uvicorn waits for every request handler before it runs the app's shutdown, which is where the sessions are closed, and it waits without end unless told how long. `SessionsFirstServer` therefore ends the sessions first (`SessionManager.shutdown`, which closes them all at once and is safe to call again from the lifespan), so a request that waits for a worker in the middle of a run is answered at once and the worker and its scratch directory go with the session; `timeout_graceful_shutdown` (`_GRACEFUL_SHUTDOWN_SECONDS`) bounds what is left. A handler that waits on something other than its socket must also be ended by a shutdown: `ws_job_events` (`api/routes/jobs.py`) waits on a queue, and a second task reads the socket for its end (a client that left, or the close uvicorn sends every socket when it is asked to stop); the socket of a streamed run waits for the run's next event, so a driver that is cancelled finishes its buffer first (`_drive_streaming_run` and `_drive_sweep` both do), which is the event that ends every stream attached to it. uvicorn raises the signal it shut down on again as it returns, and with the default handler a SIGTERM ends the process on the spot, inside `server.run`: `_stop_signals_held` notes the signal instead, and `serve` raises it once more after it has stopped what it started (the background code generation). `tests/integration/test_serve_shutdown.py` holds a real server to the time it has, to its exit status and to leaving no worker and no scratch directory.
- `server/src/tensa/desktop.py`: the window `tensa desktop` shows the UI in (the optional `desktop` extra, pywebview). `run_window` serves on the socket the CLI bound in a thread and runs the window's event loop on the main thread, which every toolkit requires; when the window closes it sets uvicorn's `should_exit`, and the shutdown that follows ends the sessions and their workers. `load_webview` is the one import of `webview`, so nothing else needs the extra, and `install_command` is the one pip command the help and every message give (the `desktop` extra only when the installed tensa declares it, with Qt added on Linux, in double quotes so that `cmd.exe` takes it too). `check_window_support` is what the command asks before it makes the workspace or starts a server: on Linux a display and a toolkit that starts. It finds the second out by starting each installed toolkit in a child process (`probe_toolkit`, in pywebview's own order), because Qt aborts the process when a system library such as `libxcb-cursor0` is missing, which Python cannot catch and a parent can see. The toolkit that starts is asked for by name when it is not pywebview's first choice, and when none does the command stops with one message: what each lacks, the command that installs it, and that `tensa serve --open` needs none of it. A bundled executable starts no child (its `sys.executable` is the program itself) and only warns.
