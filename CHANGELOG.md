# Changelog

All notable changes to TENSA are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/), and the project adheres to semantic versioning once 1.0 lands.

## [Unreleased]

### Added
- A time-domain run can close a frequency loop on a battery: `controllers` on `POST /sessions/{id}/tds` and on the WebSocket's `start_tds` frame. A closed-loop study needs something that reads the frequency while the run goes and tells a battery what to deliver, which with ANDES alone is a Python function on `TDS.callpert`, and a server cannot take a function from a client. So a run takes the parameters of controllers the server has, and nothing that is evaluated. There are two kinds. A `droop` commands `gain` MW per Hz of deviation beyond a `deadband`, discharging when the frequency is low and absorbing when it is high, up to `p_max` (left out: the device's own limit, the smaller of `pmx` and its current limit `ialim`). An `ffr`, a fast frequency response, waits until the frequency is `trigger_deviation` Hz below nominal or falls `trigger_rocof` Hz/s or faster, commands `power` MW for `hold` seconds and lets go; it fires once a run, and a negative `power` makes it answer a high frequency. Both take a `ramp` in MW/s, a sample `period` (0.1 s unless given), a `t_start`, and the frequency they read: `coi`, the inertia-weighted speed of the synchronous machines in service, or `bus`, what the device measures at its own bus. A controller commands a device of ANDES's distributed generation group (`ESD1`, the battery the element builder adds, and `PVD1`, `EV1`, `EV2` from a case file) by writing the device's external power input `Pext0`, in MW over the system base, on top of what it held; the device's own limits and state of charge decide what is delivered. Two controllers on one device add up. `GET /sessions/{id}/tds/controllers` lists the devices of the loaded case that can be named, each with what it can deliver in MW and the ANDES variables that show a controller at work on it. A batch run returns what each controller did under `controllers` (when it first acted, when an FFR let go, its peak and its last command, and every sample: time, frequency, command, the device's output and its state of charge), a streamed run puts the same without the samples in its `done` frame, and a line for each controller goes into the session's messages. **Timing**: a controller samples at the first instant ANDES has solved at or after each multiple of its period and holds its command until the next, so a command applies from the instant it was computed from, and a step the solver retries is not sampled twice. **What is refused**, with 422 and before anything is set up: a kind or a field the server does not know, a device the case does not have, a model no controller commands (a governor has an auxiliary input too, but a unit of it means something else in each governor model), `coi` on a case with no synchronous machine, and a controller on a device whose `Pext0` an Alter event also writes. When the run ends, however it ends, each device's input is what it was. A later run on the same System that names the same controllers and starts where this one stopped carries them on, so an FFR that has fired does not fire again. A reload or a restored snapshot puts another System in place and the controllers start afresh on it, so an FFR that fired before a snapshot was taken can fire again in a run that goes on from it. Sweeps do not take controllers. The MCP `run_tds` tool takes `controllers`, and `list_tds_controllers` lists the devices. The module `core/tds_controllers.py` and contract 13 in `server/ANDES_VERSIONS.md` say what it rests on.
- The TDS tab has Frequency control. Add a controller opens a form with the kind (a droop or a fast frequency response), the device it commands (the batteries and distributed generators of the case, each with its bus and what it can deliver), the frequency it reads and its numbers, sized from the device to start with: a droop that reaches the device's limit at half a hertz, a fast frequency response of the whole limit for ten seconds at 0.1 Hz. A value the server would refuse is refused beside its field. Each controller is listed in words (`80 MW per Hz of the system frequency beyond ±0.02 Hz, up to the device's own limit`) and can be edited or removed, and a case with no such device says so and has an Add a battery button that opens the battery's form. The controllers go with the next run, together with the variables that show them at work (what each device was told to add, `Pext`, its current and its state of charge), which the plot lists under ANDES variables. When the run ends the page says what each controller did, and the TDS tab keeps that beside the controller. They name devices of the loaded case, so they are forgotten when another case is opened.
- A battery can be added to a system: ANDES's `ESD1`, the distributed energy storage model, is now one of the models `POST /sessions/{id}/elements` builds and `GET /topology/schema` describes. The builder had the renewable converters (`REGCA1`, `REECA1`, `REPCA1`) and no storage. An `ESD1` takes over a static generator on its bus when a time-domain run starts (`gen`, a PV or Slack there), starts at that generator's power-flow output, a negative one charging it, and integrates what it delivers into its state of charge, the variable `pIG_y ESD1 <idx>`, which a run records when it is named in `dae_vars`. It is listed with the controllers in the topology, counts as a dependent of its bus, can be tripped with a Toggle, and `alterable_params` now offers its power set-points `pref0` and `Pext0`, so an Alter steps what it delivers during a run. A battery the case file holds can have its numbers changed after a run through the clone routes (xlsx cases; PSS/E has no `.dyr` record for the model). **Two per-unit bases**: ANDES reads the limits `pmx`, `qmx`, `qmn` and `ialim` per unit of the battery's rating `Sn`, and the set-point and the output per unit of the system base. On a 100 MVA base a battery with `Sn = 50` and `pmx = 1` delivers at most 0.5 pu, and a set-point of 0.4 pu is 40 MW, not 20. The megawatts and the state of charge are right either way (it moves by the delivered MW over `En` each hour at any `Sn`), but the same number is a different power on each side, so a study that sizes the battery in per unit is off by the ratio of the bases. An add that leaves `Sn` out therefore gets the system base, where ANDES's own default is 100 MVA whatever the base, and an add or edit that sets another `Sn` is accepted and answered with a warning in the session's messages. **What is refused**, with the reason, where ANDES takes the value and the run fails or misleads later: an `En`, `Tf` or `EtaD` of zero (the first step is singular), an efficiency outside 0 to 1, a `SOCinit` outside `SOCmin` to `SOCmax` (simulated as given), a `pqflag` other than 0 or 1 (fails `setup()`), trip points that do not rise or a nominal frequency outside `ft1` to `ft2` (the battery is tripped from the first step, which is what `fn = 50` alone does), and a `gen` that names no static generator or one on another bus. The pre-setup edit route and the clone route apply the same checks. The module `core/esd1.py` and contract 12 in `server/ANDES_VERSIONS.md` say what each rests on.
- The Add element panel has the battery: a Battery tile in the Component library opens its form, and it is ESD1 battery, under Storage, in the kind picker. A note above the form says what it needs first (a PV generator on its bus, whose `p0` is the power it starts at and whose `v0` should be the voltage the bus already has, or the converter cannot carry the reactive power the run starts with), to keep `Sn` on the system base and why, how to plot the state of charge and how to step the power during a run. The form opens with `Sn` set to the case's system base, active power given priority, the power limited to the rating (`pmx = 1`), one hour of energy at that rating (`En` in MWh equal to `Sn` in MVA, with a line under it saying that this is the form's value and the battery meant has its own) and the name set to the idx, so the generator is all that has to be picked. On a bus without a static generator, the warning under `bus` has a button, Add a PV generator on bus N, that opens the PV form on that bus. A line under each field whose name does not say what it holds explains it (the bus, the static generator, the rating, the limits, the energy, the state-of-charge window, the efficiencies, the frequency trip points), and a rating that is not the system base gets a warning under the field that works out what the power limit then comes to ("at most 0.5 pu on the system base (50 MW)"); it does not block the add. A state of charge outside `SOCmin` to `SOCmax` is said under the field as it is typed, before the server refuses it. The battery is in the Toggle and Alter forms of Add disturbance as well. The idx the form proposes for an exciter, a governor or a battery now follows the ones the case already has (`ESD1_2` after `ESD1_1`), and one that is taken is refused in the form: until now every controller was offered `<model>_1` again.
- The form of a device that takes over a static generator (a GENROU or GENCLS machine, a battery) ties its `bus` to its `gen`. They were two unrelated lists, the buses with nothing to say which of them has a generator and the generators with nothing to say where they are, while the device has to be on its generator's bus. The bus list now names the generators on each bus (`BUS2 (generator: PV 2 used by GENROU_2)`), the generator list gives each one's bus and the device already on it, and picking either sets the other where there is one answer, with a line under the field that moved. A bus without a PV or Slack generator gets a warning that says to add one there first. So does a generator a device already takes over: left at their defaults both start at its whole output and the time-domain run does not initialize (a battery put on PV 2 of IEEE 14 beside GENROU_2 fails with a 0.4 pu mismatch at bus 2), so the form says to add a PV generator for the new device alone. Neither warning blocks the add. The Add element command is found under "battery" and "storage" in the command palette, and the line under the Component library says that the form's Kind list has the models without a tile (machines, exciters, governors).
- Adding an element starts from more places. The Case card at the top of the sidebar has an Add element button beside Change case: the Component library's tiles open the same panel, but they sit at the foot of the sidebar, below the fold of a short window. A right-click on a bus of the diagram offers Add element here, which opens the panel on that bus: every form with a bus field opens with it chosen, the panel says which bus it is on, and it stays on it for the next element, so a PV generator and then the battery on it are two short forms. A device that needs a static generator gets the one on that bus when no other device uses it yet, also when the generator reaches the case while the form is open. A right-click on the background offers Add element. While nothing can be added (a run has locked the system, the case is still loading) each of these is greyed out and says why.
- The topology the server returns now has `base_mva`, the system MVA base: the header of a PSS/E RAW file, `baseMVA` of a MATPOWER file, the `_config` section of an xlsx or json file, and ANDES's default of 100 for a case that sets none and for a blank system. It is what a per-unit power on the system base is turned into megawatts with, and what the Add element panel compares a battery's rating to. It is `null` when the configuration has no usable value.
- Continuation power flow takes options, and says what the generators did. `POST /sessions/{id}/cpf` had a direction (`load` or `gen`), a step and a step count. It now also takes `enforce_q_limits`, `stop_at` and two more directions, each for that run only, and its result has grown to match. **Reactive limits**: `enforce_q_limits` switches a PV or slack generator to a PQ bus held at `qmin` or `qmax` where its reactive power gets there as the load grows. ANDES documents `pv2pq` as working during CPF, and as shipped it does not: the routine evaluates the limiters as if every step were the first iteration of a power flow, so no generator switches along the path and the nose is the one of a system with unlimited reactive power (on IEEE 39 the load grows by 113% without limits, by 36% with only the generators the power flow already held, and by 14% with every limit enforced). The server makes the limiters check at every evaluation, places each switch by bisection, to within 0.001 in the units of the continuation step (a limiter left to itself switches at the first iterate past a limit, which with the routine's long steps put the nose of IEEE 14 7% early and followed it with a jump to a negative lambda), and ends the path at a switch it cannot get past: a generator held at `qmax` whose voltage would rise above its set-point is not at its limit at all, and following the equations on from there, as the routine alone does, ends with buses at several per unit. The continuation starts from the power flow as solved, so solve that with `enforce_q_limits` too; a request that would hold a generator the power flow left past a limit is refused with 409 and says which generators. **Direction**: `load-only` grows the loads and leaves the PV generators, so the slack supplies the increase, and `custom` takes `load_increase` (`idx`, `p`, `q` per PQ load) and `generator_increase` (`idx`, `p` per PV generator) in MW and MVAr for one unit of lambda. A direction moves PQ loads and PV generators, which is what ANDES's routine moves: other load models stay as they are and the slack takes up the difference. A device the case does not have, the slack generator, or a direction that moves nothing is a 422. **Lower branch**: `stop_at: "full"` goes on past the nose and follows the low-voltage solutions back to lambda 0. **Result**: `generators` holds every in-service PV and slack generator's reactive power in MVAr at every step, with its limits, and `limit_events` the generators held at a limit, each with the step and lambda at which it got there (step 0: held by the power flow). An event marked `at_nose` means the nose is where that generator ran out of reactive power, a limit-induced collapse and not a smooth fold of the curve, which is what a margin study needs to tell apart. `q_limits_enforced`, `stop_at`, `direction` and `complete` say what was run and whether it finished; a full curve whose lower branch breaks off keeps its nose (`truncated` stays false). `POST /sessions/{id}/cpf/qv` takes `enforce_q_limits` as well and returns the same generator data; a QV curve still stops at its nose. One thing stays as ANDES has it and is reported, not hidden: its limiter never lets go, so a generator held at a limit stays held where its voltage has come back across the set-point and a real exciter would take over again (typically one the power flow holds at `qmin` while the load grows). Each event's `would_release_step` says from which step that is the case. Nothing of a run is left in the session: the limiter flags, which the routine does not restore with the rest of the base case, are put back with the solver settings. The module `core/cpf_options.py` and contract 11 in `server/ANDES_VERSIONS.md` say how each of these reaches ANDES.
- The CPF tab has the options a study turns on. The form had a Run button and, behind Advanced, two directions and two solver fields. It now shows what grows with λ: Loads and generation, Loads only, Generation only, or Custom, whose two tables take the MW and MVAr each PQ load gains and the MW each PV generator gains for one unit of λ, with each device's solved power beside the field and a button that fills them with the base values to edit from. A box asks for the lower branch as well, and Enforce generator Q limits holds each generator at its limit from where it gets there. That box is the power flow options' own switch, not a second one: the curve starts from the solved power flow, so both run under one setting. When it is ticked and the last power flow left generators past a limit, the form names them and has a button that solves the power flow again with the limits on; a run the server refuses for that reason offers the same, and the notice goes once the power flow has been solved again. The QV curve has the same box. Step and max steps stay behind Advanced, each saying what it does: Step is only the first step, since ANDES sizes the ones after it itself and moves λ by half a unit a step at most. The custom direction says how large its numbers have to be, which is any size: λ counts multiples of them, so ten times the numbers is the same curve at a tenth of the λ, and under the tables the form adds up what one unit of λ changes beside the base case's own totals. Small increases make a long path, and a run takes 500 steps unless Max steps says otherwise. A run that uses them up, before the nose or on the lower branch, says so under the Run button with how far it got, and has a button that runs it again with four times as many; the number goes into Max steps and stays there for the next run. The line that sums up the last run sits beside the Run button, because the curve is below the options and out of sight in a short drawer. The browser now waits three minutes for a CPF, where it gave up after one: a full curve with limits on a 2000-bus case takes most of a minute.
- What the generators did along a CPF curve is shown under it. A panel plots each PV and slack generator's reactive power against λ, with a chip per generator to add or remove it and its Qmin and Qmax shown when it is pointed at. It lists the generators held at a limit with the λ at which each got there, and says in a sentence whether limits were enforced and, when the nose is where a generator ran out of reactive power, which one. Markers on the λ axis of the curve show where each generator reached its limit, a full curve draws its lower branch dashed, the readout under the slider gives both branches' voltage, and a caption names the direction and what one unit of λ is. Where a held generator's voltage has come back across its set-point, the panel says from which λ, and that ANDES keeps it at the limit all the same. The curve's CSV gains a column per generator and says in its header what was run and which generators were held; the panel exports its own CSV and PNG.
- COMTRADE export of a time-domain run. A run could leave the app as CSV and nothing else. The export menus of the plot (Export plot) and of the timeline (Export run data) now have COMTRADE (.zip): an IEEE C37.111 record of the plotted series, or of every column of the run, as a `.cfg` and an ASCII `.dat` named for the case and the run (`ieee14_1a2b3c4d.cfg`) in one archive. It is the 1999 revision, the one readers most widely take. Each series is an analog channel with the unit the run streams it in (`pu`, `rad`, `MW`, `MVAr`; an ANDES variable recorded by name has the unit `NONE`, since the run does not carry ANDES's unit for it), scaled over its own range onto the integers the format holds, so a channel resolves about 1 / 200 000 of that range, and every sample has a time stamp in microseconds. A run with an event in it is not sampled at a fixed rate, so its record declares none and a reader goes by the time stamps; an evenly sampled run declares its rate. The station is the case the run was computed on, the device is the run's label, and the date is when the run started. The values are phasor quantities, one per output interval, not the instantaneous waveforms a recorder stores. The server writes the record, from `POST /comtrade`, which holds no session: the body is `t` and `channels` (each a `name`, its `values` and an optional `unit`), so `t` and `variables` of a batch run's `traces` go in as they come out, with optional `name`, `station`, `device`, `frequency_hz`, `start_time` and `trigger_t` (a fault's time). It answers with the `.zip`, and with 413 for more than 5,000,000 values (channels times samples), which the menu checks before it sends anything and says what to do about. A run kept from an earlier session exports the same way, after a reload and with no case open. The example client has a `comtrade()` method.
- An HTML report. The Reports dialog showed ANDES's plain-text reports, to read there or copy out as LaTeX. Save as HTML, in that dialog, and Export HTML report, in the Export menu and the command palette, now write one self-contained file of what the study came to. It has the power flow (how it converged and with which settings, the system totals, the limits it breaks, and every bus, line, generator and load with its name); the comparison of the two kept power flows the Compare tab is showing; the time-domain runs kept, with a chart of each quantity on the plot for the runs that are plotted (in the units the plot shows, as vector graphics that stay sharp in print) and a table of each series' initial, lowest, highest and final value; the eigenvalues, least damped first, when an eigenvalue analysis has run; and ANDES's own reports as an appendix. The file needs nothing else to open: its style and its charts are inline, it carries no script, and its own content policy forbids scripts, network requests and forms, since the names in it come from case files. It is named `<case>_report_<time>.html`. Once a time-domain run has moved the system on, the report gives the last power flow that was solved (from the kept ones), not the state the run ended at, and it can be made after a reload, with no case open, from the results the browser kept. The command is greyed out, with what to do first, until there is a result to put in it. The Reports dialog, which was Report in the Workspace menu, is now Reports… there and in the Export menu, under Export HTML report.
- Results now survive a reload of the page. Finished time-domain runs and the power flows kept for comparison lived in the tab's memory, so a reload, or a tab closed by mistake, took every plot with it. The browser now keeps them (in IndexedDB, under the address the UI was opened at): a run is written when it finishes, with its samples, its name, its colour and its overlay pin, and the power flows with their names and which two are compared. When the page loads again they are back: the runs in History as earlier runs (none is the active one, since the session that computed them is gone), with the date beside the time for a run from an earlier day, and the power flows in the Compare tab. History can be opened before any case is, once there are runs to list. The page that loads says what it kept: the "No case loaded" page names the runs and power flows and has a button to each, the empty plot says how many earlier runs there are and opens the run history, and Run history, with the number of runs, is in the Run menu and beside the plot's export menu as well as behind the top bar's History button, which most windows are too narrow to show outside the More menu. A run that was still streaming when the page was left is not kept. What is deleted from the lists is deleted from the browser too: Delete and Clear runs in History, the retention limit pushing a run out, Delete in the Compare tab, and Change case, which discards the session and everything with it; its confirmation says so, and that opening the other case from Saved cases keeps them. Two tabs open on one address share what is kept: a tab that loads starts with the results of the other, and what either deletes is deleted from the browser for both. The other tab still lists it until it is reloaded, and if it is a run, that tab asks before it is closed or reloaded, since the run is then nowhere else. The retention limit set in the TDS tab is kept as well, so a reload does not push out runs a higher limit was holding. Where the browser has no IndexedDB to give (some private windows) nothing is kept and everything else works as before; if a write fails because the browser's storage is full, a notice says so once and the run stays in the tab. The server's own error text for a failed run is not written to the browser.
- Two power flows can be compared. The last ten converged power flows are kept, each with the case it was solved on and the names of its elements, and a Compare tab in the Analysis drawer sets two of them side by side: A, the reference, and B. For every bus it gives the voltage of both and its change (per unit), the angle of both and its change (degrees, brought into -180 to 180); for every line and transformer the active and reactive power at the from end of both and its change, the change at the to end, of the loss and of the loading (percentage points of the rating); for every generator and load its P and Q; and the system totals. Every difference is B minus A. B follows the latest run and A is the run before it, so running, changing something and running again needs no picking, and either can be set to any result kept; Swap A and B turns the comparison round. The two results need not come from one case: elements are matched by idx, and one that only A or only B has is listed with no difference and marked. Each table starts with the largest change first and sorts, filters, copies and exports as CSV like the element tables, and a line above it names the largest change of voltage, angle and line flow and where it is. A result can be named, which keeps it while newer runs come in, or deleted. The system summary of the PF tab has a button to the comparison once a second power flow has converged, and the command palette has Compare power flows. The results stay when another case is opened, so a case can be compared with a modified copy, and go when the session is discarded with Change case.
- What ANDES says while it works now reaches the user. ANDES reports through its `andes` logger: a power flow that stopped at its iteration limit, a device whose initialisation failed, the limits a limiter adjusted, the faults and toggles a time-domain run applied. Nothing read it. The worker never configured the logger, so its warnings went to the server's console and its information messages were dropped. Each worker now captures that log while a command runs and sends it back with the reply, and a streamed run's messages ride on its frames, so they arrive while the run goes on. The server's own paths are taken out of the text before it leaves the worker: the workspace is written relative to itself (`Parsing input file "ieee14.raw"...`), the home directory as `~`, and any other absolute path, POSIX or Windows, as `<path>`. A sweep's and a report's messages are left out (a sweep runs hundreds of solves, and a report prints a summary ANDES logged when the run ended), and warnings and errors still go to the server's console as before.
- `GET /sessions/{id}/messages` returns what ANDES logged for a session: each message with its `level` (`info`, `warning` or `error`), the ANDES logger that said it, the `source` command that was running (`load_case`, `run_pflow`, `run_tds`), the time and the text. A table ANDES logged stays one multi-line message, and a message that repeats in a row is kept once with a `repeat` count, even when the repeats arrive in different replies or frames of a streamed run, so a warning ANDES prints on every step of a long run is one message and cannot push the load and power-flow messages out of the log. A message whose count grows is numbered again, so a client that reads on by number gets it once more with the larger count and replaces the one it holds that says the same. `after` reads on from a message number (pass back the `next_after` of the last read), `level` gives that level and above (`level=warning` is warnings and errors), and `limit` caps the page. A read does not go to the worker, so it answers while a run is in progress. The session keeps its latest 2000 messages, counts what was lost in `dropped`, and numbers messages for good, so a client that kept its place is not confused by a clear. `DELETE` on the same path empties the log. The MCP server has a `get_messages` tool and the example client a `messages()` method.
- Two things a power flow does that ANDES never logs are now warnings. With reactive limits enforced, a generator that reaches `qmin` or `qmax` is switched from PV to PQ and held there, and a load whose bus voltage leaves the load's `vmin` and `vmax` (0.8 to 1.2 pu by default) is turned into a constant impedance (ANDES's `pq2z`), so it draws less than its set-point. Either changes the solution and the only trace is the limiters' flags, so after a converged power flow the worker reads them and says which generators and loads it was, as messages from the `tensa.notice` logger (up to eight are named, the rest counted). A power flow that did not converge says nothing of the sort, and neither does the one a time-domain run starts for itself.
- A Messages tab in the bottom drawer lists those messages, each with its time, level and the command it came from. Warnings and errors show at first and a toggle on each level, with its count, adds or hides it; a filter box keeps the messages that hold every word typed (in the text, the command or the ANDES module); Copy puts what is on show on the clipboard and Clear empties the server's log too. The tab carries the count of warnings and errors, red when there is an error, so a run that needs a look shows without opening it, and the list stays at the newest message while it is scrolled to the end. The tab is current while a run goes on, and Open Messages is in the command palette. When the last power flow did not enforce Q limits and generators are past one anyway (the Violations tab lists them), a note above the list says why no warning names them, and has a button that runs the power flow again with Q limits enforced and one that opens the power flow options; the Enforce generator Q limits hint now says the Messages tab names the generators held, and the Warnings toggle's tooltip says what a warning can be. Opening another case from the saved cases drops what was said about the one it replaces, so the tab and its count describe the case that is open (the server's own log is left alone, and a load that fails changes nothing).
- The Buses, Lines, Generators, Loads and Shunts tables can be edited in place. Double-click a value, or press F2 on the selected cell, type, and press Enter, Tab or click away to write it; Esc drops it, and Tab goes on to the next value of the row that can be changed. What the case holds can be changed (a bus's rated voltage, limits, area and zone; a line's `r`, `x`, `b`, in-service flag `u` and rating; a static generator's `p0` and `v0`; a load's `p0` and `q0`; a shunt's B and G) and the results beside it cannot. A limit shown in kV is typed in kV and written per unit on the rated voltage of its own bus (the new one, when the same paste sets it). The values go through the route the Inspector's pencil uses, so they can be changed until a case is run; after a run the table says so and has a Reset run button, which discards the changes made so far, and while a power flow or a run is going it waits. The cells of one device are sent in one request, one device after another, and each cell stays dimmed until the topology has been read again; a value the server refuses is explained under the bar. The tables gained the columns to edit: the bus `Vn`, the line `r`, `x`, `b` and `u`, the generator `p0` and `v0`, and the load `p0` and `q0`, which are per unit on the system base and say so (a load's `p0` read as MW showed 9.670 where the diagram showed 967.0 MW). A table with more columns than the panel holds scrolls sideways instead of cutting the headings.
- The element tables have a filter box (a row stays while every word typed is found in one of its cells, as shown or as held; sorting and the CSV export follow it), a cell cursor (click a cell or move with the arrow keys, Shift extends it to a block, Ctrl+A takes the whole table), Ctrl+C on the block as the tab-separated text spreadsheets paste (values at full precision), and a Copy button for the whole table with its headings. - `tensa serve` now generates ANDES's code in the background when it is missing. - Live time-domain streaming is much cheaper on large cases. A frame used to be an Arrow table with one column per variable, so every frame repeated all the column names and described every column, and the browser looked each column up by name. On the WECC case, with 1208 variables, that was a 134 KB frame for 9.7 KB of values, 9.4 ms to encode and 11 ms to decode. The names now go out once, in `stream_start` (`metadata.var_columns`, as before), and each frame holds only `t` and one `v` list column with the row's values in that order: 10 KB, 0.1 ms to encode and 0.2 ms to decode on WECC, with the browser matching values to names by position. Frames are still Arrow IPC, so any Arrow reader opens them, but a client that read columns by name from each frame must now take the names from `stream_start`; `tensa.core.stream.decode_batch` is the reference reader, and `stream_start.metadata.schema_version` is now `2.0`. `numpy`, which ANDES already requires, is now declared as a direct dependency of the server.
- The time-series plot no longer destroys and rebuilds its charts on every streamed frame. Each frame produced a fresh description of every chart, and the plot read a fresh description as a different chart, so during a live run each stacked chart was torn down and created again at the frame rate (two groups at 30 frames per second meant about 60 chart builds a second). A chart is now created once and fed each frame in place, and is rebuilt only when what it shows changes: the variables selected in its group, the theme, a run's colour, or the set of overlaid runs. The in-place update re-ranges both axes, so the time axis still grows with the data.
- The single-line diagram's layout engine (ELK) no longer runs on the UI thread, and no longer runs more often than it has to. ELK is 1.4 MB of what used to be a 2.76 MB main script, so every visit downloaded and parsed it, and every layout froze the page while it ran. On the 179-bus WECC case, opening the case kept the main thread busy for 1.7 s in one measured run (longest stretch 0.83 s). The engine is now its own file (`assets/elk-worker.min-*.js`), fetched the first time a layout is needed and run in a Web Worker. The main script is 1.3 MB, the same load keeps the main thread busy for 0.5 s (longest stretch 0.29 s), and the diagram it draws is identical. A layout also used to start every time the topology was fetched again, which happens after each power-flow run, reload and parameter edit. It now starts only when a bus or the terminals of a branch change, and not at all when the saved layout already places every bus: a case you have arranged by hand, or IEEE 14 and 39 by file name, which have a built-in layout. If the worker cannot start (a blocked script, or a content security policy that forbids workers), the diagram falls back to the grid layout it already used when ELK failed, instead of waiting forever.
- Snapshots no longer write or try the ANDES solver-state (dill) blob unless asked. The blob cost about 2.5 s and 2.3 MB per save on IEEE 14, and a restore with it reloaded the case and replayed every disturbance first, then threw that work away when the blob loaded, so the "fast path" took the same 0.17 s as a plain replay. ANDES 2.0 also cannot load a blob saved after the power flow but before the TDS is initialised on a case with dynamic models (`IndexError` in `load_ss`), so for a case with a `.dyr` it tried the blob, failed, and replayed anyway. A save now writes only the JSON metadata (about 6 ms) and a restore replays it. `POST /sessions/{id}/snapshot` takes `include_dill`, `use_dill_optimization` on `POST /sessions/{id}/snapshot/restore` now defaults to false, and with the opt-in the restore skips the reload and replay. The Save snapshot dialog has an "Also save the solver state" checkbox, the Load snapshot checkbox starts unticked and is enabled only for a snapshot that has a blob, and the "Force replay (debug)" switch is gone because replay is the default. Overwriting a snapshot without the blob also deletes the blob it replaces, so an opted-in restore never loads stale state.
- A sensitivity sweep no longer restores the snapshot before every iteration. Each iteration used to load the case, replay the snapshot's disturbances, set up and solve the power flow, only to read back a disturbance log that cannot change during the sweep, then load the case a second time and let the TDS run solve the power flow again. The log is now read once before the loop, and an iteration reloads the case, adds the disturbances with the swept value, and runs the TDS. Results are identical (same step counts and convergence on IEEE 14 and IEEE 39), and each iteration takes about 40% less time when the simulation is short, for example 0.76 s down to 0.46 s on IEEE 14 with a `.dyr` file at `tf` 0.2 s and a 0.01 s step. A snapshot that cannot be used (missing, corrupt, a target past its log, a disturbance of the wrong kind) still shows as an error on every iteration, but is now found once and no longer touches the session's System.
- A sensitivity sweep of four or more values now runs its iterations in parallel. The server starts up to `--sweep-workers` extra worker processes for the sweep, no more than half as many as there are values so that each gets at least two iterations to pay for its start-up (about a second), hands each worker the next iteration as it becomes free, and stops them when the sweep ends. The results are the same as a sequential sweep's (the same convergence, final times, and step counts on IEEE 14 and IEEE 39, and a session built from scratch works too), and they are reported in iteration order whatever order they finish in, so the progress bar, the WebSocket events, and resuming with `last_iteration` behave as before. With four workers, 16 iterations of IEEE 14 (2 s at a 0.01 s step) went from 30 s to 9 s, and the same on IEEE 39 from 21 s to 6.8 s. Aborting a sweep stops every worker in the middle of its iteration, cancelling its job ends them at once, and a worker that dies loses only the iteration it was running: that iteration shows as an error, like one that diverged, and the others finish. If every worker dies the sweep ends with the error category `SweepWorkersLostError`, not `WorkerDied`, because the session itself is fine and the sweep can be started again. The session's own worker takes no part, so a parallel sweep leaves the session's System as it was, where a sequential one leaves it holding the last iteration. A sweep of three values or fewer, a snapshot the session cannot read, or workers that fail to start or are gone before any of them has taken the case run on the session's own worker as before. Each worker has the same BLAS thread caps as a session's worker, so on a machine with few cores set `TENSA_WORKER_THREADS` or `--sweep-workers` lower if the workers crowd each other.
- A new session's worker now imports ANDES while it waits for its first command, so the first case you load is no longer slower than the rest. The first `load_case` in a fresh worker spent about 1.0 s on IEEE 14 importing ANDES, its model modules, pandas, scipy and openpyxl, where a load in a warm worker takes 0.2 s. The web UI opens a session when the page loads, so by the time you pick a case the imports are done: with a few seconds between opening the session and loading, that first load went from 1.2 s to 0.35 s through the session manager. The worker skips the warm-up when a command is already waiting, so a script that opens a session and loads a case at once is not delayed, and a warm-up that fails changes nothing, because the load imports whatever is missing. ANDES's generated code is not imported ahead of time on purpose: ANDES reloads it for every System it builds, so doing it early saved nothing in a measurement.
- The plots no longer redo work on every streamed frame that did not need doing. The variable picker read the whole runs map, so each frame re-rendered it and classified every column name again (1208 of them on the WECC case); it now reads only the runs' column names, which do not change while a run streams, and is left alone. The overlay plot merged the pinned runs' time axes once per stacked chart, hashing every row of every run (a `Set`, a sort and a `Map`), and did it again for every frame of a run that was not pinned at all. It now merges the runs in one linear pass that all the charts share, and ignores frames of runs it does not show. Merging and resampling five pinned runs of 4000 rows into three stacked charts took 20 ms per frame in a Node measurement and now takes under 5 ms (128 ms and 8 ms at 20000 rows). The single-line diagram's streaming overlay also looked up the bus-voltage columns again on every animation frame; it now finds them once per run.
- The web UI loads much less before it can draw. The main script was 1.3 MB (388 kB gzipped) and held every panel, dialog and charting library, whether or not the session ever used them. It is now 466 kB (137 kB gzipped), with React in a second file of 194 kB (61 kB gzipped) that a release rarely changes. The rest is fetched the first time it is needed: the single-line diagram (React Flow and its layout code, 230 kB) when a case is first shown, the Arrow decoder (168 kB) when the first time-domain run starts, the Analysis tab with the plot and uPlot (92 kB) and the EIG, CPF and SE views (54 kB) when they are opened, the PNG rasteriser when the first PNG is exported, and the command palette, shortcut cheatsheet, and the report, bundle import and export, history, sweep, snapshot, PMU and profile import dialogs when each is first opened. The first load is 729 kB of script and styles (210 kB gzipped), down from 1384 kB (402 kB gzipped), and the build no longer warns about a chunk over 500 kB. A page left open across an upgrade that can no longer fetch one of these files shows a "Reload page" prompt in the panel, or a toast for a dialog each time you try to open it, instead of going blank. A unit test (`web/tests/unit/lib/codeSplitting.test.ts`) walks the import graph from `main.tsx`, so a stray static import cannot quietly undo the split.

It had grown to 514 kB, so the five element tables (Buses, Lines, Generators, Loads, Shunts) and the virtual-list package they share now load in chunks of their own, when their tab in the bottom drawer is shown, and the entry chunk is 487 kB. API JSON and the UI's scripts and styles are compressed: `/openapi.json` goes from 170 kB to 38 kB on the wire and the 466 kB main script to 137 kB. Responses under 1 kB, WebSockets, and bodies that already carry a content encoding are sent as they were. Every file under `assets/` has a content hash in its name, so it is served with `Cache-Control: public, max-age=31536000, immutable` and a repeat visit fetches none of them. `index.html`, which names the current hashes, is served with `no-cache`, so a browser asks again, gets a 304 when nothing changed, and picks up a new release on its next load. Source maps stay out of the wheel and the sdist, as before.
- Reading the values of each streamed step is about ten times cheaper on large cases. The worker looked every generator up again at every step through ANDES's `SynGen.get` (a dictionary lookup per generator for each of the two variables), copied each line array to a Python list element by element, and evaluated the line flows and the window mean in Python loops. It now works out where every value lives once, when the run starts, and reads ANDES's arrays with numpy at each step. On the 1208-column WECC case collecting a step takes 0.07 ms where it took 0.68 ms, and the whole per-step hook (collect, aggregate, encode) takes 0.11 ms where it took 0.84 ms with a 30 Hz boxcar mean. The values are identical to the old ones, checked step by step through a fault on WECC, NPCC (21 GENCLS and 27 GENROU machines) and IEEE 39. A bus, line or load array that is missing is now logged once per run, where it was logged at every step, and an infinite angle gives `nan` columns for that line instead of raising. The per-group `collect_*` functions in `tensa.core.stream` are replaced by one `StreamCollector`.

### Fixed
- The list of ANDES variables in the TDS tab comes back by itself. The server answers one request a session at a time and refuses a second with 409, and the tab showed a refused list as "The session is busy with a run" until the search was changed, also when nothing but another list had been in the way. A list that is refused is now asked for again, a few times at once and then once every two seconds while the refusal stands, so it is there when the run ends, as its message says; the message stays up until then. The list of devices a controller can command is asked for the same way.
- After an add, the Add element form proposed the idx it had just used. The form is reset for the next element a moment before the topology has the new one, so a second bus, generator or battery in a row was offered the idx of the first and refused as taken until it was typed over. The proposal now follows the case until an idx is typed.
- A refusal from the server stayed under the Add element form after the value it was about had been corrected, until the next add. It goes at the first edit.
- An element added to a loaded case could leave the case unable to set up. A reference to another device (a load's `bus`, a machine's `gen`, an exciter's `syn`) was passed to ANDES as the client sent it, and a JSON client, the Add element panel among them, sends `"5"` where a RAW or xlsx case holds the bus as the integer 5. ANDES took the text and failed at the next power flow with `device not exist with idx=5`, after which the session had to be reloaded; a line added that way had also lost its voltage base, since no bus was found to read it from. `POST /sessions/{id}/elements` and the edit route now match every reference to the idx the case holds, whichever way it is sent, for every model the builder takes (which parameters are references is read from the ANDES model itself). A reference that names no device is left as sent, for ANDES to refuse.
- An add that left out a parameter ANDES has no default for (`gen` of a GENROU, `bus` of a load, `pqflag` of a battery) answered 422 and corrupted the session all the same: ANDES counts the device in before it reads its parameters, so the idx stayed on the model with parameter lists one short, a second add of that idx made a second device, and the next setup, power flow or time-domain run failed on the mismatched lists (`operands could not be broadcast together`). Such an add is now refused before ANDES is called, with the names of what is missing, and adds nothing.
- The QV curve's `max Q` was not a reactive power. The result's `max_lam` was ANDES's own continuation parameter, a fraction of the range the run sweeps, while everything else in a QV result is on the axis of the reactive power at the bus: IEEE 14's bus 5 showed `max Q = 1.1706` for a curve that reached 5.87 pu. It is now the largest reactive power the curve reached, in the summary, the chart header, the CSV and the API.
- A continuation power flow in the generation direction (`direction: "gen"`, Generation in the CPF form) failed every time with a 422 reading `len() of unsized object`: the routine was handed the number 2.0 where it takes a target for each PV generator. It now gets each generator's own output doubled, and a case with no PV generation to scale is refused with a reason.
- A CPF request's `step` and `max_iter` stayed in force for every later request of the session. They were written to the routine's configuration and never taken back, so after one run with a small step count, runs that asked for nothing were cut short the same way until the case was reloaded. They now apply to the run that carries them.
- A report no longer gives away where the server keeps the case file. ANDES heads its power-flow and eigenvalue reports with the full path of the case file, and `GET /sessions/{id}/report` passed that on: the Reports dialog showed it, and a report copied or saved out of it carried it along. The worker now takes the server's paths out of the report's text and tables before it leaves, the same way as for the messages ANDES logs, so the header reads `Case file: ieee14.raw`, relative to the workspace.
- The Reports dialog now fits the window. A power-flow report with its tables is taller than most screens, and the dialog grew with it past the top and bottom of the window, where neither its title nor the end of the report could be reached. It is now held to the window's height with the report scrolling inside it, and it is as wide as it was meant to be (its width was written where the dialog's default width overrode it).
- Clicking a machine in the Generators table, or in the new Machines table, showed the static generator with the same idx in the Inspector, since a case such as Kundur numbers its GENROU machines and its Slack and PV generators alike and the selection held the idx alone. The selection now names the model of the row, so the Inspector shows the machine, with its own parameters and the exciter and governor attached to it.
- `PUT /sessions/{id}/elements/{model}/{idx}` checks every value before it writes any, so a refused one leaves the device as it was. A numeric parameter given as null, as text that is no number, or as a nan or an infinity is refused with a 422: the pre-setup parameter list took anything, a line's `r` of `"abc"` failed later in ANDES, and a GENROU reactance of null made the machine's next reactance edit fail with a server error. A GENROU's `H` must be a number above zero (a boolean, a negative value and a nan used to land as an inertia), and a reactance the machine holds as a non-number is refused with a message and not a server error.
- `PUT /sessions/{id}/elements/GENROU/{idx}` now takes the inertia constant `H`, which the schema lists for the model but ANDES has no parameter for (it holds `M`, equal to 2H, which is what adding a machine converts `H` to); the edit used to be refused as not editable. An edit that gives both `H` and `M` is refused, since the two could disagree. A change to a GENROU reactance is checked against the ordering the machine needs (`xd > xd1 > xd2 > xl`, and the same on the q axis) on the values the machine holds, and refused with a 422 that names the pair. Adding a machine was already checked and editing one was not, so a value could be put out of order and the time-domain run went unstable later. Only an ordering the edit takes part in is checked, so a case whose data already breaks a pair elsewhere can still be edited, and a set sent in one edit is judged as a set, whatever the order of its values.
- Variable tree elements now sort numerically when their idx is a name that ends in a number, so `GENROU 10` follows `GENROU 9` and not `GENROU 1`.
- A generator or load on a bus that is out of service is no longer reported as producing or drawing its set-point, and a shunt on one no longer counts in the power-flow summary. ANDES keeps such a device's own `u` at 1 and writes its effective status `ue` (0) into the bus equations, so the rows and the summary read `ue`. The summary's bus shunts now also include switched shunts (at the admittance they have switched to) and time-domain shunts, which left it out of balance on a case that has them.
- A generator or load that is switched off (`u` of 0) is no longer reported as producing or drawing its set-point. `generator_outputs` and `load_consumption` gave a PV generator's `p0` and a load's `Ppf` whatever `u` said, though ANDES zeroes them where it writes the bus equations, so generation, load and losses did not add up on a case with a device out of service (the slack carried the difference unseen). Both rows now read 0, and the Generators and Loads tables, the diagram and the new system summary agree.

The development-mode command in the README and `CONTRIBUTING.md` now passes `--allow-origin http://127.0.0.1:5173`, without which the Vite dev server's requests got a 400. The From source steps and demo commands now have PowerShell equivalents for everything that only worked in a POSIX shell, and say that Windows on ARM is not supported (`kvxopt` and `pyarrow` publish no wheels for it). `web/README.md` described the removed token login and linked to plan files that are not in the repository; it now matches the app.

These and several "v0.1" and "Phase A" qualifiers are corrected, with `web/src/api/generated.ts` and the GUI-parity ledger, and a test now fails on promise-about-the-future wording in the schema or a description that names a route that does not exist.

The flagship spec (`web/tests/e2e/load-pf-flow.spec.ts`, the one the end-to-end job under Development runs) is rewritten for the current UI and no longer needs a token. The other four files (seven tests) stay skipped, with a note that their selectors predate the current layout. The comments in `web/playwright.config.ts` now describe how the tests run: against the build the substrate serves, or against the Vite dev server with `tensa serve --allow-origin http://127.0.0.1:5173`.
- Dialogs that close themselves after a success (Import and Export bundle, Save snapshot, Load snapshot, Save system, Save as custom case) left their timer running after the dialog went away. Closing one by hand inside that window and reopening it let the old timer close the new dialog, and dismissing it with Escape while its request ran did the same once the answer arrived. The timers are now cancelled when a dialog closes and none starts after it has, including the three-second confirmation on the Load snapshot Delete button. A Save system that answers after its modal was dismissed still writes the layout file but no longer touches the modal that is open now.
- `tensa serve` with the default OS-assigned port (`--port 0`) rejected the web UI's own requests with `400 bad-origin`: the Host/Origin allow-list was built from port 0 before the real port existed, so the browser's `Origin: http://127.0.0.1:<port>` never matched. The server now binds its listening socket first, builds the allow-list from the real port, and serves on that same socket, so the printed URL always works. `--open` now works with any port, including the default (it used to refuse port 0), and `--reload` with port 0 picks a free port up front. On Windows the socket asks for exclusive use of the port instead of `SO_REUSEADDR`, which there lets another process share it.
- The time-domain step size `h` was silently ignored: it was written to `TDS.config.h`, which ANDES never reads, so every run used the 1/30 s default. `h` now sets `TDS.config.tstep`, and the trapezoidal integrator steps at exactly the requested size in batch runs, streaming runs, and sweeps. The TDS report now shows the step actually used. The QNDF integrator still chooses its own step (ANDES ignores `tstep` there), so bound it with `max_step`. The API and UI wording for `h` now says so and no longer claims a 1/120 s default.
- Workspace path handling on macOS: the lookup that canonicalizes case files called libc's variadic `fcntl` through ctypes without a prototype, which passes the buffer where the callee does not look on Apple Silicon, so loading a case could fail there. It now uses the standard-library `fcntl`. The workspace root and the parent folders of files written back (layout sidecars, saves) are canonicalized the same way, so `--workspace ~/Cases` on a folder stored as `~/cases`, or with a different Unicode normalization, no longer rejects every load as outside the workspace.
- Workspace paths that cannot be resolved now return a 4xx instead of a 500: permission denied on a parent folder (layout read/write), and on Windows a missing file or an invalid file name (`WinError 123`) when loading a case.
- Saving the single-line-diagram layout returned a 500 on Windows with Python 3.12: `os.fchmod` does not exist there before Python 3.13, and the missing attribute was not the `OSError` the code expected. The call is now skipped where the platform lacks it and the file mode is still applied after the write.
- File names that Windows reads as something else are now refused on every platform, so a workspace, bundle, or snapshot made on Linux or macOS still works once it reaches Windows: DOS device names (`CON`, `nul.txt`, `COM0` to `COM9`, `LPT0` to `LPT9`, `CONIN$`, `CONOUT$`, any extension or case), `:`, a trailing dot or space, control characters, and the other characters Windows cannot store. The rule applies to every case file in an imported bundle (all checked before any is written; invalid entries answer 422), snapshot names, save-as names, the file name given to Save system, and the layout of a case file not yet in the workspace. A layout for a file already there is saved whatever it is called, snapshots saved under a name that is now refused can still be listed, restored, and deleted, and the snapshot name check also rejects a trailing newline that the old pattern let through.
- Bundle import and Save system no longer write through a symlink in the workspace. A link whose target does not exist yet slipped past the check, and the write then created the file wherever the link pointed, outside the workspace if it pointed there. Such a link is now refused before anything is written.
- The reported version was wrong: `tensa.__version__` was hard-coded to `0.1.0.dev0` while the package is 0.4.0, so the OpenAPI `info.version` and the `tensa_version` stamped into exported bundles and saved snapshots named a version that never existed. It is now read from the installed package metadata, so `server/pyproject.toml` is the only place it is set, and `web/package.json` (which said 0.0.1) now matches. Run from a source tree where tensa is not installed, it reports `0+unknown`. After bumping the version, reinstall an editable checkout (`pip install -e ./server`) so the metadata catches up; a unit test fails until you do, and also fails if `web/package.json` or `CITATION.cff` drift from `pyproject.toml`.
- Saving a case as PSS/E `.raw` no longer depends on the platform's default text encoding. On Windows the file was written in the ANSI code page (cp1252) with CRLF line endings, and a bus name that code page cannot hold made the save fail. It is now always UTF-8 with LF line endings. ANDES sniffs a `.raw` file's encoding with chardet rather than assuming one, and before chardet 6 it mistook a UTF-8 file whose only non-ASCII text is one accented letter for Latin-1 or MacRoman and read the bus name back garbled, so TENSA now requires `chardet>=6`.
- Editing a controller parameter in a PSS/E `.dyr` clone no longer fails on, or rewrites, files saved the way PSS/E saves them. A `.dyr` in the Windows code page (an accented plant name in a comment) was rejected as invalid UTF-8, and every edit converted the file's line endings. The edit now changes only the one number and leaves every other byte alone, including a UTF-8 byte-order mark. Text after a record's `/` is now treated as a comment, as ANDES does, so a trailing comment no longer made the next record impossible to find.
- Ctrl+C in the terminal running `tensa serve` no longer prints a `KeyboardInterrupt` traceback from every worker. A terminal sends SIGINT to the whole foreground process group, so each worker raised out of its command loop and died on its own; workers now ignore SIGINT and the server stops them in its own shutdown. (A Ctrl+C in the first seconds after a session starts, while its worker is still importing numpy and ANDES, is not covered.)
- Each worker now limits its numerical libraries to 4 threads by default (`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`, `VECLIB_MAXIMUM_THREADS`, `NUMEXPR_NUM_THREADS`). Before, every worker started one BLAS thread per core, so a few sessions on a many-core machine fought over the cores. A variable you have already set is left alone. OpenBLAS, MKL and numexpr use `OMP_NUM_THREADS` when their own variable is unset, so if you set `OMP_NUM_THREADS` (to 1, say, or to 8) the variables you did not set take that count instead of 4, and `GOTO_NUM_THREADS` is likewise left to OpenBLAS. `TENSA_WORKER_THREADS=N` sets all five to `N` whatever else is set. The values are put in the environment as the worker starts, because numpy reads them while it loads.
- On Windows, workers now die with the server. Linux and macOS workers already exited when their parent did, but Windows has no equivalent, so a killed server left its workers running. Each worker is now placed in a Job Object that Windows closes, workers included, when the server process ends. If the Job Object cannot be set up, a warning is logged and the session starts normally.
- A server that was killed (SIGKILL, a crash, power loss) no longer leaves its clone-on-write scratch folders in `<workspace>/.sessions/` forever. Each folder records which server owns it (process id, host and container, start time), and the next `tensa serve` on that workspace removes folders whose owner is gone or whose process id now belongs to another process. A folder with no record, a record that names no host, or one written on another host or container is removed only after 24 hours untouched, and a folder of a server still running on the same host is never touched. Closing a session on Windows also now deletes a clone of a read-only case file, which the cleanup used to skip silently.
- The warning for case files that read outside the workspace compared paths with a plain string prefix, so a sibling folder such as `cases2` counted as inside a workspace named `cases`, and it recognized Python's own files with a Linux-only path pattern. It now compares whole path components (ignoring letter case where the platform does) and finds the interpreter's own files from the interpreter's prefixes and site directories, so it also works with Homebrew, conda, and Windows installs.
- A trapezoidal run after a QNDF run on the same session ignored the requested step size `h` and kept taking QNDF-sized steps. QNDF leaves ANDES's fixed-step switch (`fixt`) at 0 on the System's configuration, and ANDES keeps the QNDF integrator object when a run resumes. Each run now sets `fixt` for the integrator it asked for (an explicit `fixt` override still wins) and replaces a leftover QNDF integrator with the trapezoidal one. The reverse switch works only until the first step, because QNDF needs history that ANDES's initialization builds. A QNDF run after an eigenvalue analysis, which initializes without stepping, now builds that history and runs. A session that has stepped, in a time-domain run or in a snapshot restored from one, answers 422 with a message that names that cause and asks for a reload, instead of quietly running trapezoidal.
- A step size `h` that is zero, negative, NaN, or infinite is now refused wherever it enters. ANDES accepts such a value and quietly makes the rest of the session variable-step. `POST /tds` already rejected `h <= 0` but let `Infinity` through, the sweep request had no check, and a WebSocket `start_tds` frame passed the value on unchecked, so a non-numeric `h`, or an integer too large to be a float, raised unhandled. All of them now answer 422 (REST) or an error frame (WebSocket) before a worker is involved, and a sweep fails once instead of recording an error for every iteration.
- The `tstep`, `max_step` (`dtmax`), and `fixt` entries of `tds_config_overrides` skipped that check and were written to ANDES's configuration as sent, so `tstep: 0` still left the session variable-step. A `tstep` of 0 or less, a negative `max_step`, a `fixt` other than 0 or 1, and a NaN or infinite value in any override are now refused with a 422 (REST) or an error frame (WebSocket) that names the key, before anything is written to the session.
- A streamed time-domain run announced the wrong step mode and refused too late. Its `stream_start` frame reported fixed or variable step from the session's leftover `fixt` setting, which the run had not set yet, so a first QNDF stream, or a trapezoidal stream after a QNDF run, carried the wrong `fixed_step` and the wrong decimation algorithm (`boxcar-mean` versus `boxcar-mean-best-effort`). It now follows the requested integrator and any `fixt` or `tstep` override. A run the server refuses, QNDF on a session that already ran trapezoidally or an unknown `tds_config_overrides` key, is now refused before the stream starts, so the client gets the error and no start frame, and the session's configuration is left as it was. The `POST /tds` 422 for the QNDF refusal now ends with one hint to reload instead of three.
- A time-domain run the server refuses over the WebSocket (QNDF on a session that has stepped) ended its error with "call reload_case() to recover", the Python API's wording, which means nothing in a browser. It now says to reload the case and how: `POST /api/sessions/{id}/reload`, or Reload from file in the Edit menu. The web UI also shows the server's whole message now, not the copy in the close frame, which is cut to fit. That cut counted characters, so a message with accented characters could overrun the 123 bytes a close frame holds, the close failed, and the client never received the 4500 code. It now counts bytes, and a client's own text quoted back in an error is cut to 40 characters.
- A time-domain request the server refuses before it writes anything (a step size `h` or a `tds_config_overrides` value that is not usable, or an override key ANDES does not have) no longer tells the caller to reload. It was reported as a failed `setup()` ("ANDES setup() failed: ... call POST /api/sessions/{id}/reload to recover") with a `reload-case` recovery, so the web UI offered a Reload button although the session was untouched. It is now a plain 422 that gives the problem and no recovery action (REST), or an error frame without the reload hint (WebSocket), and it has its own error class, `TdsRequestError`. A refusal that does need a reload, such as QNDF on a session that has already stepped, is unchanged.
- A layout path that runs through a file, such as `case_path=ieee14.raw/x.raw`, answered 500 on Linux and Windows (macOS already answered 400). Anything that is not a directory is now rejected with a 400.
- Exporting a bundle no longer writes case files that import would refuse. A workspace file such as `con.raw`, `case_12:30.raw`, or `.hidden.raw` loads on Linux and macOS, but the bundle holding it failed import everywhere, and an edited case named `con.raw` exported as `con.xlsx`. Export now answers 422 with the name of the file and asks for a rename, and also answers 422 when the case has more than 16 case files, the most an import accepts.
- On Windows, restoring or deleting a snapshot whose name Windows reads as a device (`aux`, `con.v2`) is now refused like a new save. Such a snapshot cannot exist there, so the exemption for older snapshots only reopened device-name access; Linux and macOS are unchanged. The layout exemption for existing case files and the snapshot exemption now follow the same platform rule, and on Windows the snapshot list no longer shows a name that restore and delete would refuse.
- The sdist could not be built into a wheel: `python -m build` and any install from the sdist failed with `License file does not exist: ../LICENSE`, because `server/pyproject.toml` read the license from `../LICENSE` and force-included `../web/dist`, and an unpacked sdist has neither. `server/LICENSE` is now a copy of the license (a test keeps them identical) and a build hook, `server/hatch_build.py`, replaces the `force-include` table. The sdist carries the built UI as `src/tensa/static`, so a wheel built from it serves the UI, a build with no UI still fails with a message to run `pnpm build` instead of producing a package that answers 404 at `/`, and `pip install -e ./server` works before `pnpm build` has run and no longer leaves a stale copy of the UI in site-packages.
- The wheel shipped the UI's source maps, about 10 MB uncompressed that a browser only fetches when its developer tools are open. The wheel and the sdist now leave out every `*.map` file.
- `pip install 'tensa[mcp]'` installed version 2.x of the MCP SDK, and `tensa mcp` then exited with a message saying the extra was not installed. SDK 2.0 renamed `FastMCP`, which the server imports. The extra is now `mcp>=1.28.1,<2` (1.28.1 is the first release past its published advisories). `tensa mcp` was checked end to end against 1.28.1 and 1.30.0: it starts a private `tensa serve`, lists its tools, and answers a call. Moving to the 2.x name is a separate change.
- On Windows, two jobs updated back to back could not be told apart by time: the monotonic clock there ticks about every 16 ms, so equal `updated_at` values fell back to insertion order. The `409` that names the job holding a busy session could then name the wrong one, and the activity panel could order jobs wrongly. Job timestamps are now strictly increasing.
- When a failed job was merged into an earlier identical failure, the final update sent to the activity panel for the merged job still took its time from the raw monotonic clock, so on Windows it could tie with, or sort before, the update of the job it was merged into. It now uses the same strictly increasing clock as every other job update.
- `SessionManager.shutdown` now takes the sessions it closes out of the registry, as closing one session already did. It left them there, so each session's worker handle and abort event (five POSIX semaphores) lived as long as the manager, and a manager kept alive by a reference cycle (an app object in a test, for one) let the cycle collector free them at an arbitrary moment. When that moment fell inside the start-up of Python's multiprocessing resource tracker, the full test run printed `ResourceTracker called reentrantly ... might leak` warnings. No semaphore was lost, and the warnings no longer appear in the suite. Two integration tests that held the exception they provoked in a local, another reference cycle that kept a session's worker handles, no longer do.
- On Windows, the warning for case files that read outside the workspace logged a line for a path that contains a NUL byte, which no file can have and whose open fails anyway. POSIX already skipped it; the check no longer depends on the platform.
- The first test of the abort acceptance suite failed on a fresh CI runner with a read timeout. It loads IEEE 14 with httpx's default 5 s limit, and ANDES generates its Python code for the models on the first load on a machine, which takes longer. The acceptance helpers now allow that first load up to 180 s.
- The Save snapshot dialog test that fills the name field through the native setter no longer waits on a timer, and a new test covers a dialog that unmounts inside its auto-close beat. That case is what made the old test fail on a loaded CI runner, before the timer fix under the dialogs bullet above.
- Streamed frames that batched several steps carried the wrong times. ANDES hands the per-step hook one array for the time and updates it in place, and the stream kept that array instead of its value, so every row of a frame sent with `decimation: "none"` and a `max_rate_hz` had the time of the step that closed the window, and a boxcar-mean row was stamped with that step's time instead of the mean time of its window (up to a step late). The time is now copied when the row is buffered.
- `AGENTS.md` described a precomputed ANDES cache that ships in the wheel (`server/src/tensa/cache/`). There is none: the code ANDES generates lives in `~/.andes/pycode`, written on first use or by `tensa warm-cache`. The guide now says so, and where the cache check lives.
- A missing file under `assets/` (or any other missing path that ends in a file extension) now answers 404. It used to answer with `index.html` and status 200, as if it were a client-side route, so a browser that asked for a script or a source map that was no longer there got HTML and reported a MIME type error instead of the missing file. With the UI split into chunks this is what a page left open across an upgrade runs into.
- A client that fell behind a live time-domain stream got a stream with frames missing, and could wait forever for the end of the run. Each attached client has an inbox of 10000 events, and when it was full the server dropped whatever did not fit and said nothing, the run's end marker included. A client that reaches that point now gets the same `resync` message as a client past the resume buffer, with a `reason` saying it fell behind, and the socket closes. The run never waits for a client, so a slow one neither slows the solver down nor changes what the other clients receive; it is told instead. `AGENTS.md` and the worker's docstring described credit accounting at a credit ceiling that never existed. They now say what paces the solver: the blocking write to the data pipe, which follows the parent's reads.
- Run TDS with disturbances after a power flow no longer sends a request that is certain to fail. The button committed the disturbances first, got a 409 because the power flow had already committed the System's setup, then reloaded the case and committed again, leaving a failed `disturbance-commit` job in the history on every such run. When the topology already says the System is committed, it now reloads first and commits once. A finished run commits the setup and returns no topology, so the UI reads the topology again when a run ends (after the read of the final operating point, because the server refuses a read that arrives while another is in flight). The 409 recovery remains as a fallback for a topology that lags the server, and a run with no disturbances still needs no reload.
- The warning for a live time-domain stream cut short was worded for one of its two causes. The server sends `resync` when a reconnecting client asks for frames that left its resume buffer and when a client falls 10000 events behind a live run, but the UI answered both with "Connection dropped too long; partial buffer retained", which is false for the second since that connection never dropped. `resync` now carries a `cause`, `buffer_evicted` or `client_lagged`, next to its `reason` (a message with none is taken as `buffer_evicted`), `RunStream` reports `client_lagged` as its own error code, and a client that fell behind is told that its tab fell too far behind and to reset and re-run for the whole stream. The reconnect wording is unchanged, and `llms.txt` and the WebSocket docs describe `cause`.
- A session was reaped after three minutes without a request even while its browser tab was open, so a user who stopped for a while, or stepped away with a case half built, came back to a session with no case in it. The tab now checks in with `GET /api/sessions/{id}` every 30 seconds, which the server counts as activity, so a session lasts as long as its tab (and three minutes after it closes). The same check tells a tab that slept through the timeout, or outlived a server restart, that its session is gone as soon as it wakes, so recovery starts then and not on the next click. A tab left open now keeps one of the `--max-sessions` slots until it is closed, and `--idle-timeout-seconds` should stay above 60.
- Recovering from a lost session now brings back the edits, not just the case file. When the server lost a session (reaped while the tab slept, or gone with a restart) the UI reloaded the case file into a fresh session, so added elements and edited parameters were gone and a system built from scratch was reported lost. The UI now keeps an in-memory journal of the edits it sent (element adds, edits, deletes and undos, clone-on-write controller edits, and the reloads that revert them) and replays it in order after the reload or after recreating the blank system, then says how many changes came back; a reload drops the entries it would undo, and a refused edit ends the replay. What it cannot replay (PMU and profile placements, a snapshot restore, a bundle import) still falls back to reloading the file and reporting the unsaved edits lost. The topology, snapshot, PMU and profile queries also wait for a recovery to finish: they used to reach the replacement session before the recovery's own case load and make it fail with a 409, which left the UI on a case with no topology, and a load or replayed edit that still finds the session busy is now retried.
- A PNG export no longer loses the styling of SVG content. The rasteriser copies an `<svg>` as markup and does not visit what is inside it, so anything styled by a class, which is how the charts set their fills, strokes and label sizes, came out black, without its gridlines and with oversized labels. The export now writes the computed paint of every SVG element in the exported panel into the copy before it is rasterised, and puts the page back afterwards.
- Loading a second case left the first case's results in force. The store module that wires the cascade between slices was no longer imported (it went with the token login), so after a power flow, an EIG run or a TDS run, loading another case kept the old results: Run EIG was enabled on a case that never had a power flow and failed when clicked, Run PF stayed disabled with a stale reason, and the diagram drew the old case's voltages and frames over the new one. The cascade is wired again, and a case change now also drops the EIG, CPF and SE results and releases the active TDS run. Finished runs stay, with their names, colours and overlay pins, so a run can still be overlaid with a run on a modified copy, until the session ends. Reload case and Reset run also drop the EIG, CPF and SE results, whichever Analysis tab is open.
- Run EIG, Run CPF, Run QV-curve and Run SE showed why they were disabled only in a tooltip, so a first-time user saw a greyed-out button and no reason. The reason now sits under the button as text (and is the button's accessible description), with the fix next to it: Run power flow, which starts the power flow itself, or Reset run. SE says outright that Generate Measurements builds the measurement set from the solved power flow and no measurement file is needed, and Generate Measurements is the highlighted button until it has run. The QV-curve tab says to choose a bus. The Run PF button in the top bar keeps its reason in the page for assistive technology, and the "Run power flow" button on a failed EIG, CPF or SE run (it used to only switch views) now runs the power flow.
- While a case loaded, which can take a while the first time because ANDES generates code for its models, the diagram and the Case panel still said "No case loaded" and the Run buttons were disabled without a word. They now say "Loading <file>...", the file's row in Saved cases shows it, and the Run buttons give that as their reason.
- The first-run hint after the first power flow sent users to an Analyze panel "on the right"; EIG, CPF and SE are under the Analysis tab of the bottom drawer, and it now says so.
- The 409 messages for EIG, CPF and SE without a converged power flow quoted ANDES internals ("EIG._pre_check warns but does not short-circuit on non-converged PFlow"); they now say the routine needs a converged operating point. The SE message for missing measurements now reads as a sentence, with the endpoint in parentheses.
- The power flow result gave every dynamic machine a generator output of 0 MW, 0 MVAr and 1.0 pu, and on a case that numbers its machines like its static generators it overwrote the real output of each generator with that zero row (on `kundur_full` the result held four rows of zeros, so the Inspector and the Buses table showed no generation). ANDES gives GENROU and GENCLS no `p` or `q` before the time-domain run initialises, so the extraction made the values up. `generator_outputs` now holds the static generators (PV and Slack) only, with their real output; read a machine's output from the row of the generator it names in `gen`. The Inspector and the plots panel do that, and say "No PF output for generator ..." for a machine that names none instead of showing zeros.
- The Generators table showed a dash for every GENROU and GENCLS machine, and for the reactive power of every PV generator, and printed the per-unit active power setpoint of the case as if it were MW (7.000 under "P (MW)" for a generator the diagram shows at 700.0 MW). Its P and Q columns now read the output of the last power flow in MW and MVAr, as the diagram and the Inspector do, a machine reading the output of the static generator it names, and stay a dash until a power flow has converged. Hovering the P or Q heading says where the figures come from.
- The Inspector could show an edited value that the case no longer held. It kept a copy of each value saved with the pencil, to show it before the server answered, and never dropped it. After Reset run or Reload from file put the file's values back, the Inspector still showed the edited `vmin` while the diagram and the server used the file's, and an edit made on one bus also showed on the next bus selected. The copy now belongs to the topology entry it was made on, so a reload, a refresh or another selection shows the case's own value.
- The time-series plot no longer flattens a quantity that shares an axis with one far larger. A bus's voltage (about 1 pu) was drawn on one axis with its angle (tens of degrees), and a generator's speed (1 pu, moving by thousandths) with its rotor angle, so the voltage dip and the speed swing plotted as nearly flat lines. Each chart now keeps the voltage or the speed on the left axis, scaled to its own range, and draws the angles on a second axis on the right, in degrees. A single run's chart dashes them. A chart that overlays runs draws a run's angle in the run's own stroke instead, since there the dash names the run, and the axes' labels tell the voltage from the angle.
- The time-series plot was a sliver in the bottom drawer. Its charts shared the height left after the controls took theirs, which was 60 px or so of a chart, with its axes cut off, and the legend that names the traces sat below the chart's box and was clipped away. A chart now keeps a height it can be read at, the panel scrolls for what does not fit under it, and the plot is made shorter by the height of its legend so the legend stays in view. A chart is now titled for what it draws: "Bus voltage" when only voltages are plotted, "Bus voltage and angle" when both are, where it used to say "Bus voltage / angle" with no angle on it.
- A fault scheduled on one case was still scheduled after another was opened, and the next time-domain run committed it to the new case, to whatever bus had the same idx, or had it refused with a 422 when there was none. Opening another case, clearing it, or the end of the session now clears the scheduled disturbances. Recovering a lost session keeps them.
- Emptying a time field of the disturbance form wrote NaN into it, and typing after that gave "NaN1.3", and a negative amount could not be typed into the Alter form at all, because a half-typed value ("-") is not a number and the field was rewritten from the spec. The fields now keep the text being typed. The fault form's labels also say what its times are ("Fault applied at", "Fault cleared at") instead of tf and tc, and tf is also the final time of a run.
- The full-window results page is restored after a reload while the results are not, so it could be the first thing a returning user saw, empty and with the diagram hidden. It now has a Show diagram button of its own.
- The plot's Variables toggle had the same name as the heading inside the tree it opens, so a lookup by that name found two elements. The toggle now reads Choose variables and counts the series plotted, and the tree's heading reads Plotted series.
- Save system and Import bundle in the command palette did nothing. They told a dialog to open that only existed while the Workspace menu was open. The dialogs are now always available, and the menu items open the same ones.
- The single-line diagram could not be zoomed out far enough to show a whole case in a short pane. React Flow stops at half size, and a fit of IEEE 14 in a window 900 px high needs 0.45, so the top and bottom of the diagram sat outside the pane, the zoom-out button was dead, and a bus, machine or line out there could not be reached to right-click or drag. The diagram now zooms out to a tenth of its size, and Fit view reaches all of it.
- The flow arrows on the single-line diagram are sized against the largest branch flow of the case instead of a fixed 1000 MW. On a 100 MVA case such as IEEE 14, whose largest flow is about 157 MW, every arrow was between 7 and 8.2 px, so a line carrying nothing and the busiest line looked alike; the busiest line now draws the biggest arrow (15 px) and the rest in proportion.
- The Loads table labelled the per-unit setpoints of the case as MW and MVAr, so Kundur showed a load of 9.670 where the diagram showed 967.0 MW. P and Q are now what each load draws in the last power flow, in MW and MVAr, as the Generators table already shows its output, and read a dash until power flow has run. The column headings say where the figures come from.
- The right end of the top bar (Search, Theme, History, Help) scrolled out of sight on a laptop-width window. Its controls need about 1460 px once a power flow has run and about 1750 px while a time-domain run streams, so a 1280 or 1440 px window cut them off. They now hand over to a "..." More menu at the right end of the bar as the window narrows: below 1820 px Search, Theme and History go there, below 1620 px the four pane toggles (sidebar, inspector, drawer, results view) too, and below 1400 px the Labels and Units toggles as checked items. Each item runs the command of the control it replaces and names its key, and Help stays in the bar. The bar still scrolls below about 1100 px. An end-to-end test checks the widths in a real browser, after a power flow and while a time-domain run streams.
- Saving the system over the case file it was loaded from (`POST /sessions/{id}/save` with that name and `overwrite`) left the session as if the file were unchanged. The worker kept its record of the elements added since the load, so a later Undo last addition or Delete reloaded the file, which by then held those elements, and added them again: the same idx twice, and an undo that removed nothing. Such a save now empties the record, and the file is the session's base. It is refused with 422 while the system holds disturbances a client committed or a bundle import or snapshot restore replayed, because they would be written into the case file and come back as its own events. A save under any other name is unchanged.
- A Generator, Load or Transformer tile of the Component library opened the Add element form with no form in it, only "No schema for model "Generator"." (and the kind picker showing Bus), because the form is for models and the tiles name families. The panel now opens a tile on the most common model of its family, PV generator, PQ load or Transformer (2W), with the picker one click from the others.

## [0.4.0] — 2026-07-05

### Changed
- **Renamed the project from "ANDES App" to TENSA** (Transients, Eigenvalues & Network Simulation Application). The Python package, CLI command (`tensa serve`), MCP server, default workspace directory (`~/.tensa/cases`), and repository (github.com/Roger-GO/TENSA) all follow. ANDES remains the simulation engine and is credited unchanged; only this project's own identity changed. Existing installs: reinstall with `pip install -e ./server` and move cases from `~/.andes-app/` if you used the default workspace.

### Added
- Showcase demo: a captioned video of an agent building WSCC 9-bus from scratch through the UI and running every analysis, embedded in a rewritten, production-ready README.
- First-run example cases: an empty workspace is auto-seeded with IEEE-14, Kundur, and WSCC-9.

### Changed
- Relicensed from MIT to **GNU GPL v3.0** to match ANDES, which TENSA is built on. Added an ANDES citation (Cui et al., 2021) to the README.
- GENROU exposes its full subtransient reactance + time-constant set, with d/q reactance-ordering validation that names the offending value (prevents textbook transient values silently clashing with unset subtransient defaults).
- Eigenvalue scatter: numeric axis ticks + gridlines, points colored by damping band with a legend, and an "All modes" filter toggle so a well-damped system isn't an empty plot.
- Bus data grid now shows net per-bus P/Q computed from the power-flow result.
- Branding: logo, favicon, and "TENSA" wordmark.

### Fixed
- Single-line diagram readability: buses render as traditional busbars; branch/feeder taps land on the bar instead of floating off it; each bus's machines and loads sit on the face pointing away from the network (a bottom bus's machine hangs below it, not up through its own feeder) with short, non-crossing stubs; edge flow labels render above bus boxes.
- Result charts: continuation-power-flow traces now get a distinct colour per bus (single-digit bus names no longer collapse into one band) with a labelled per-λ voltage readout; the eigenvalue scatter uses smaller markers, a larger plot, and a discoverable zoom/pan hint; CPF/EIG/SE charts no longer overflow and clip at the bottom of the full-screen results view.
- A crashed per-session worker now returns a clean `503` with "reload the case or start a new session" guidance instead of leaving a zombie session that errors on every call; snapshot dill-restore falls back safely instead of crashing the worker.
- Snapshot/disturbance list and layout-sidecar reads return `200` (empty/null) instead of `404`/`409`, removing browser-console error noise.

- TDS run badge distinguishes "Halted at t=X" (non-converged) from "Done at t=X".
- Continuation power flow no longer 500s when it doesn't converge (NaN tails are truncated to the finite curve).
