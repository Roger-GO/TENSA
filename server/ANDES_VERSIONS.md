# ANDES_VERSIONS.md

Phase A pins ANDES to `>=2.0,<3.0`. The substrate depends on **eleven API contracts** that ANDES does not formally declare as public API — they are documented here so that an ANDES upgrade can be reviewed against this matrix before it lands.

## The eleven API contracts

| # | Contract | Where the substrate uses it | Failure mode if it changes |
|---|---|---|---|
| 1 | `andes.System.models` introspection — enumeration of all model classes (Bus, Line, GENROU, etc.) with their `idx` lists | `core/wrapper.topology_snapshot()` to build the topology summary | Topology endpoint missing or duplicating elements |
| 2 | `Fault`, `Toggle`, `Alter` model param shapes — kwargs accepted by `ss.add('Fault', ...)`, `ss.add('Toggle', ...)`, `ss.add('Alter', ...)` | `core/disturbance.py` translates substrate `DisturbanceDef` payloads to these kwargs | `DisturbanceDef` schema breaks on disturbance creation |
| 3 | `TDS.callpert` per-step hook — assigning a callable runs it once per integration step | `core/wrapper.run_tds()` and `core/stream.py` for streaming + abort polling | TDS streaming silently degrades or hangs |
| 4 | `dae.ts` time-series structure — `dae.ts.x`, `dae.ts.y`, `dae.ts.t` arrays grow during TDS | `core/stream.py` reads from these for state-variable snapshots | Streaming returns wrong column shape or no data |
| 5 | `andes.load(path, addfile=..., setup=False)` semantics — load without committing setup so disturbances can be added | `core/wrapper.load_case()` and `reload_case()` | `add_disturbance` always raises post-setup; v0.1 disturbance flow broken |
| 6 | **`PFlow.run()` and `TDS.run()` require an explicit prior `ss.setup()` call.** Verified empirically against ANDES 2.0.0: `PFlow.run` on a non-setup System raises `IndexError` because `dae` has no allocated address space. ANDES does NOT auto-call setup from these routines. The wrapper calls `ss.setup()` first if `not ss.is_setup`. | `core/wrapper.run_pflow()`, `run_tds()` | If a future ANDES version starts auto-calling setup, the wrapper's explicit `ss.setup()` call becomes a no-op-with-warning and we must handle that case rather than treating "second setup returned False" as a failure. |
| 7 | `sys.audit("open", ...)` event coverage — Python-level open() calls from ANDES are visible to the audit hook | `core/wrapper` --strict-fs best-effort logging of secondary file reads | --strict-fs misses reads (caveat already documented in the trust model — C-extension reads are not caught even today) |
| 8 | **Power-flow settings live on the System, not in `config`, once it is built.** `PFlow.config.tol` and `max_iter` and `Bus.config.flat_start` are read while the solver runs. `PV.config.pv2pq` is not: the `PV` and `Slack` models copy it into their `qlim` `SortedLimiter` (`enable`) when they are constructed, so writing the config of a loaded System does nothing. The limiter's own `enable` is the live switch, and its flags (`zl`, `zu`, `zi`, `ql`, `qu`, `nql`, `nqu`) stay where a run leaves them, `check_var` returning early once it is off. Verified against ANDES 2.0.0. | `core/pflow_options.pflow_options_applied()`, used by `core/wrapper.run_pflow()` | A renamed or relocated limiter attribute makes `enforce_q_limits` silently do nothing (the integration tests in `tests/integration/test_pflow_options.py` fail), and a flag the limiter stops resetting would carry one run's generator limits into the next. |
| 9 | **ANDES names and places its time-domain variables itself, and drops some of them.** `dae.x_name` and `dae.y_name` hold `"<variable> <Model> <idx>"` (the model name is not repeated when a string idx already has it, and underscores in the idx become spaces) and are filled by `System.set_dae_names` only when `TDS.init()` runs; before that they are empty or hold the power-flow variables. A static device that an online dynamic model replaces (an `IdxParam` with `replaces=True`) loses its algebraic variables in `DAECompactor.compact_dae()` during `TDS.init()`; its `var.a` then points at other variables. Verified against ANDES 2.0.0. | `core/dae_vars.dae_variables()` lists the names from `System.find_models`, each model's `states`, `algebs`, `idx` and `idx_params[...].replaces`, with no setup; `core/stream._DaeReader` reads `dae.x` / `dae.y` at the position `dae.x_name` / `dae.y_name` give each name, which is the only address that is right after compaction | A changed name format or a changed rule for what is compacted makes a name the catalogue offers unreadable: its stream column is `nan` and the worker logs that it is not in `dae.x_name` or `dae.y_name`. `tests/integration/test_dae_vars.py` compares the catalogue with `dae.x_name` / `dae.y_name` of three bundled cases and one with a machine out of service, and every column with the model's own array at every step of a faulted run. |
| 10 | **ANDES reports through the standard `andes` logger and installs no handler of its own.** Every ANDES module logs to `logging.getLogger(__name__)`, so its records reach the `andes` logger. A handler and a level exist only after `andes.config_logger` runs, which `andes.main.run` and the `andes` command do and `andes.load` does not, so a process that does not call it has the default level (warnings and errors) and passes those to Python's last-resort handler on stderr, while the information messages are dropped. A table (an adjusted-limits report, a TDS summary) is one multi-line record. ANDES 2.0.0 logs nothing when a PV bus switches to PQ at a Q limit or a PQ load turns into an impedance; the limiter flags are the only record (`qlim.zl` and `qlim.zu` of `PV` and `Slack`, see contract 8, and `vcmp.zl` and `vcmp.zu` of `PQ`, which stay where a converged run leaves them even after the generators' `enable` is put back). Verified against ANDES 2.0.0. | `core/messages.WorkerLogCapture`, which the worker installs on the `andes` logger and lowers to `INFO`, ships back with each reply, and the Messages tab and `GET /sessions/{id}/messages` read; `core/pflow_notices` reads the flags after a converged power flow and says what ANDES does not | A renamed logger, or an `andes.load` that starts configuring handlers, leaves the Messages tab empty or prints each warning twice. `tests/integration/test_messages_api.py` and `tests/integration/test_worker_messages.py` read a real worker's messages for a load, a power flow, a non-converging power flow and a faulted run, and `tests/integration/test_pflow_notices.py` checks the flags against a case that holds generators at a limit and one whose loads are pushed under 0.8 pu. |
| 11 | **A continuation run is steered and read through three private methods of the CPF routine and the live attributes of the reactive limiters.** `CPF._bus_vmag()` is called once for every point the routine keeps, and once more for a last point it refines (a full curve's return to `lambda = 0`), each time right after `CPF._corrector(lam, xy_prev, lam_prev, step, z, dfg)` returned `(success, niter, lam)` for it. `CPF._dfg_dlam(lam)` gives the derivative of the equations with respect to lambda at the current state. The routine evaluates the limiters with `niter=0, err=1.0`, so the `qlim` `SortedLimiter` of `PV` and `Slack` switches a generator during CPF only when its `min_iter` is 0 (a live attribute, copied from `PV.config.min_iter` at construction): with the default of 2, ANDES's documented "`pv2pq` also applies during CPF" keeps the generators the power flow held and switches no other. The limiter latches: a generator it holds is never let go, also where its voltage comes back across the set-point. A step whose corrector fails is halved, and after more than ten in a row, or a step under `step_min`, the routine records a `NOSE` event at the last point it kept. `CPF.config.step`, `max_steps`, `stop_at` (`NOSE` or `FULL`) and `linsolve` are read when a run starts. `CPF._restore_base` puts back `dae.x`, `dae.y` and the set-points, and not the limiter flags. `CPF.run` takes `load_scale`, or `p0_target` / `q0_target` (one value per PQ) and `pg_target` (one per PV, an array: a bare number raises). `CPF.solver` reuses a symbolic factorisation for any matrix of the same size, which with KLU is a segmentation fault once a switch changes which entries are non-zero; `linsolve = 1` factorises afresh at every solve. Verified against ANDES 2.0.0. | `core/cpf_options.cpf_run_applied()` and `direction_targets()`, used by `core/wrapper.run_cpf()` and `run_cpf_qv()` | A renamed method or a changed corrector signature makes a run with limits answer 422 (the wrapped call raises) and leaves `generators` empty in one without; a limiter that starts switching by itself, or stops when told to, moves the nose. `tests/integration/test_cpf_options.py` checks on IEEE 14 and IEEE 39 that generators switch along the path and stay within their limits, that each switch falls at the same lambda whatever the step, that the path ends at a switch it cannot get past, that every generator is read at every step (the first equal to the power flow), and that the System, its limiter flags and the routine's config are as they were after a run. |

## Upgrade procedure

1. Bump the version range in `pyproject.toml` deliberately (never automatic).
2. Re-run the curl walkthrough (`pytest -m acceptance`) on a fresh venv with the new ANDES.
3. For each row in "The eleven API contracts," verify the contract still holds. Add a row to the verification matrix.
4. If any contract changes, update the wrapper before bumping the production pin and add a regression test in `tests/integration/`.
